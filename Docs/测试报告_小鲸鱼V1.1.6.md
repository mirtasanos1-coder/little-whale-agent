## 一、我是怎么测的（方法论）

不看代码猜功能，而是**按真实使用路径跑一遍**，再用**独立通道核验真实结果**：

1. **模拟真人发消息**：程序自带备用 Webhook（`127.0.0.1:5700`，`agent.py:87-88`），我向它 POST 标准 OneBot v11 事件（私聊 / 群聊 @ / 群聊不 @），效果等同于真人在 QQ 里敲字 → 观察程序的回复、日志、数据库。
2. **核验"真的发出去了"**：不用程序自己的日志当证据，而是调 NapCat `POST /get_friend_msg_history` 看 QQ 侧会话记录；说说则用独立脚本（`_qz2.py`，自己算 g_tk 走空间网页协议）去空间里读，确认帖子真实存在。
3. **核验"数据写没写对"**：直接只读打开 `memory\memory.db`，看 `affinity`、`care_plans`、`user_events`、`usage_log`、`feed_seen` 等表。
4. **定位根因**：现象复现后回源码找那一行（报告里每条都给了文件:行号），避免"感觉不对"这种不可修的结论。
5. **可复现**：所有注入脚本、配置修改脚本、DB 查询脚本都留在程序目录（`_inject.py`、`_cfgset.py`、`_db.py`、`_dbw.py`、`_qz2.py`），你可以自己重跑。

> 说明：为了在夜间把"定时/时段"类功能测出来，我把时段临时改成 `[0,24]`、轮询改成 15~60 秒。**测试结束后已还原**（详见第五节"我改了什么"）。

## 三、发现的问题清单（按严重程度）

### P0 —— 直接影响你点名的功能

**1）"到点来问你"（主动关心）实际永远不会自己产生**
- 现象：你说"明早九点复查，到点问我"，它回"我记着这事，明天九点后来问你结果"，但**什么都没记**。
- 证据：`user_events` 0 行、模型生成的 `care_plans` 0 行；日志里只有 `[记忆]` 没有 `[事件]`。
- 根因：`_internal\agent.py:3145` 事件提取要过 `bg_slot_ok(scope, 30)`，而记忆提取（`agent.py:3304`，同 session_key）和永久记忆（`agent.py:3409`）用**同一把全局锁**（`_BG_SLOT`）和**同一 45 秒窗口**（`_EXTRACT_MIN_INTERVAL=45`、`_BG_QUIET_SEC=8`）。三个线程由 `agent.py:4460-4463` 同时起，记忆提取先拿到锁并占用整轮模型调用（10~25 秒），事件提取 `acquire(blocking=False)` 直接失败 → **静默 return，连一行日志都没有**。
- 建议：① 事件提取别和记忆提取共用槽位（或给它独立的 5 秒小窗口重试 1 次）；② 被跳过时必须打 INFO 日志；③ 事件提取失败要有兜底（比如"用户说的时间点"用正则先落一条 `user_events`）。

**2）好友动态（刷好友空间、点赞、评论）启动后 1 小时内根本不会跑**
- 证据：`_internal\agent.py:6398-6401`
  ```python
  while True:
      _poll = max(60, int(_live_cfg("feed_poll_min", FEED_POLL_MIN) or FEED_POLL_MIN))
      time.sleep(_poll * 60)     # 先睡 60 分钟，才第一次 feed_round()
  ```
  启动 40 分钟内 `[动态]` 日志 0 条、`feed_seen` 0 行。
- 附带问题：`agent.py:6390` 打印的是启动常量 `FEED_POLL_MIN`，所以日志写"每 1 分钟刷一次"，**和实际行为相反** —— 我一开始就被它误导。
- 建议：先跑一轮再 sleep；`max(60, …)` 的钳制要么去掉，要么在日志/界面明写"最小 60 分钟"。

**3）用量统计恒为 0 → 200,000 上限保护形同虚设**
- 证据：`usage_log` 22 行，`prompt_tokens/completion_tokens/total_tokens` 全 0；直连该网关返回的是 `{"input_tokens":31,"output_tokens":8,...,"prompt_tokens":0,"completion_tokens":0,"total_tokens":0}`。
- 根因：`_internal\usage.py:93-95` 只读 `prompt_tokens/completion_tokens/total_tokens`。
- 建议：加别名回退 `input_tokens/output_tokens`。
- 影响：你以为有花费上限，其实没有；界面上的 token 曲线永远是 0。

**4）主界面（GUI）白屏卡死**
- 现象：双击 `小鲸鱼.exe`，窗口只有 `#0f172a` 背景，标题栏"未响应"，CDP 显示页面地址 `about:blank`。
- 已排除：中文路径（用 `D:\whale_test` 软链接启动一样）；缺 `_internal\index.html`（存在，533,524 字节）；`--no-frameless`（代码里根本不识别这个参数）。
- 现状判断：前端 HTML 用 Edge 能渲染（能看到「请稍等哦，马上就好~」），说明是 **pywebview → WebView2 宿主层** 没把页面导进去。内置 `Microsoft.Web.WebView2.*.dll` 是 1.0.3856.49，本机 WebView2 运行时是 155.0.4283.62，两者差距大，是最可疑的原因（未最终证实）。
- 建议：① 请作者升级打包时的 pywebview/WebView2 SDK；② 你这边可试装一个旧版 WebView2 固定运行时（如 120.x）验证；③ 短期可用 `小鲸鱼.exe --agent` 让 QQ 端功能照常跑（界面打不开不影响机器人回话）。

**5）模型配错时，界面上没有任何提示**
- 现象：你"已经配好模型"，实际 `dsv4` 在该网关根本不存在，全程只有日志里一行 `[模型] HTTP 404`，界面无红字、无弹窗，用户感受就是"机器人不理我"。
- 证据：`https://api.21r.cn/v1/models` 只返回 `deepseek-v4.1-flash`；用 `dsv4` 请求返回 `Model "dsv4" is not supported by any configured account in this group`。
- 建议：启动时做一次"模型可用性自检"，失败就在界面顶部红条提示 + 一键改回可用模型。

### P1 —— 明显影响体验

**6）`--web` 与网页版整套东西是坏的**
- `小鲸鱼.exe --web` → `web_server.main()` 用 `argparse` 解析，`--web` 未定义 → `error: unrecognized arguments: --web`，exit=2（`app_ui.py:8292` → `web_server.py:215`）。
- `README.md:1555`、`使用说明.txt:55` 都写着根目录有 `启动网页版.bat`，**根目录只有 `启动.bat`**。
- 后果：界面打不开时，本来还能指望网页版当备用，现在备用也没了。

**7）NapCat 只"装"不"配"**
- 程序只做"下载 zip + 解压"，不生成 `napcat\config\onebot11_<QQ>.json`，也不引导 WebUI 登录（`http://127.0.0.1:6099/webui?token=...`）。
- 用户视角：装完点"启动 NapCat"，QQ 能登上，但 **3000/3001 端口不通**，Agent 报"NapCat 未连接"，完全不知道还差一步。
- 另外 `launch()` 在本机 QQ 已登录时会直接拒绝（提示"先退出 QQ"），不少人会卡在这。
- 建议：装完后自动写 OneBot 配置 + 弹一段"下一步：扫码登录"的引导。

**8）说说的配额/时段只在启动时算一次**
- 把 `moment_max_per_day` 从 10 改成 1，运行时仍按 9 条跑；必须重启才生效，且界面/日志都不提示。

**9）说说去重缺失、结尾雷同**
- 4 条说说围绕同一段私聊，全以 😴 结尾。建议加"最近 N 条说说文本相似度/主题去重"和"结尾 emoji 不连续重复"。

**10）关心计划会被"对方正在聊"无限推迟**
- `agent.py:6521-6529`：8 分钟内有用户消息就跳过，且只打 DEBUG。我实测被推迟 4 分钟；如果对方一直在聊，这条关心可能永远发不出去（没有过期机制）。

**11）模型 base 末尾带 `/` 会拼出双斜杠**
- `agent.py:1431` `url = f"{base}/chat/completions"`，`cloud_base` 填成 `https://api.21r.cn/` 时变成 `//chat/completions`，这个网关直接返回非 JSON。建议 `base.rstrip("/")`。

**12）时段语义与直觉不符**
- `[8,23]` 用 `start <= hour < end` 判定，23:00 整就被排除，日志却说"8-23 点"。用户很容易以为"我设了 23 点怎么不发"。

### P2 —— 小毛病

13. 长回复按空行拆成两条消息、间隔 2 秒，像刷屏（可考虑合并或加"……"续接）。
14. `--no-frameless` 参数不生效（代码只认 `--agent/--web/--webui`），别被注释误导。
15. `feed_like/comment` 在 NapCat 侧能力探测为 False，只能走网页协议；说说读评论/回评论直接 False（功能其实没通）。
16. 表情包标签匹配偏松：情绪是"探路"也发了"打哈欠"。
17. `使用说明.txt`/`README` 与实际功能有若干处对不上（网页版 bat、`--web`、时段说明）。

## 四、优点（实测站得住的）

1. **回复质量真的像人**：口语化、有情绪、有表情包、会接前文；私聊/群聊都不像模板。
2. **落地真实**：我用 NapCat 历史反复核验，消息确实发到 QQ，不是只在日志里"假成功"。
3. **主动关心的话术水准很高**：到点发的是「复查咋样了，出来了没？昨晚紧张成那样，结果应该没你想的那么吓人吧」——只差调度那一环。
4. **容错好**：模型 404 时不会把消息吞掉（`模型不可用，本轮中止`），恢复了会补回。
5. **日志非常详细**：每个子系统启动时自报状态（能力探测、配额、时段、线程），排查成本低；`_internal\*.py` 是真源码，出事能自查——这点比多数打包软件强。
6. **配置粒度细**：时段、间隔、每日上限、静默、白名单、模型分工都能调。
7. **安全意识在**：API Key 用 DPAPI 加密、单实例锁、免责声明、注入防护模块齐全。

## 六、总结

**一句话**：这程序的"聊天内核"是合格的，甚至高于同类；但**"主动"这条线（到点关心、刷好友动态）在打包版里基本没通电**——不是模型不行，是调度和进程边界把它们掐断了；再加上主界面打不开、网页版不可用，用户很难自己发现原因。

**最适合先修的 5 件事（按性价比排序）：**

| 优先级 | 问题 | 改动量 |
|---|---|---|
| 1 | 事件提取被记忆提取饿死 → 拆槽位 + 跳过要打日志 | 小（改 `bg_slot_ok` 调用） |
| 2 | `feed_loop` 先 sleep 再跑 → 改成先跑一轮 | 极小（挪两行） |
| 3 | 用量统计别名兼容 `input_tokens/output_tokens` | 极小 |
