## 二、V1.1.7 为什么值得单独记一笔

那次是「功能都在，但用户用着不对劲」。9 个问题的共同点是**失败被静默吞掉**：

- 事件提取拿不到锁 → `return`，一条日志都不打，用户以为软件傻
- 动态循环先 `sleep` 再干活，日志却说「每分钟刷一次」
- 网关返回 `input_tokens`，代码只认 `prompt_tokens` → 用量永远 0，20 万上限的保护形同虚设

**教训（写进下一次的检查清单）**：
1. `acquire(blocking=False)` 失败必须留痕，`except` 分支必须留痕；
2. 任何「等待 / 轮询」代码，先确认「第一次执行」发生在启动后多久；
3. 读第三方响应字段，永远做别名回退；
4. 能在没有模型的情况下也应该有结果的功能（如事件提取），必须有规则兜底 —— 但兜底不许编造数据。

## 三、V1.2.0 的进程模型（进程文档）

### 3.1 进程树

```
小鲸鱼.exe (Tauri, Rust)
 ├─ 启动时 spawn ──▶ backend_server.exe --port 0        （PyInstaller onefile：引导进程 + 真身子进程）
 │                      └─ uvicorn（FastAPI，监听 127.0.0.1:5701 起第一个空端口）
 │                           └─（用户点「启动 Agent」后）
 │                              agent.py 子进程（Python）—— OneBot 备用 webhook 绑 5700
 │                                 └─ NapCat: node.exe napcat/apcat/apcat.mjs（3000 HTTP / 3001 WS）
 └─ WebView2 渲染进程（窗口）
```

### 3.2 端口契约

| 端口 | 谁用 | 说明 |
| --- | --- | --- |
| 5700 | `agent.py` 的 OneBot 备用 webhook | **永久保留**，后端启动时会跳过它 |
| **5709** | `agent.py` 的单实例锁 | **永久保留**（`INSTANCE_LOCK_PORT`，老版本是 5701，被后端抢了导致 Agent 永远起不来）；可用 `QQ_AGENT_LOCK_PORT` 覆盖 |
| 5701 ~ 5740 | `backend_server.py` | 从 5700 起往后探测第一个**空闲**端口（5700/5709 被保留，所以正常是 5701） |
| 3000 / 3001 | NapCat HTTP / WebSocket | 由 `napcat_mgr.write_onebot_config()` 写进 `onebot11_*.json` |
| 6099 | NapCat WebUI | 手机 QQ 扫码登录用 |

后端把真实端口打印到 stdout：`[backend] listening on http://127.0.0.1:5701`，
Rust 用一条线程读 stdout 抓这行（正则），再通过 `invoke('backend_info')` 交给前端。
**前端永远不写死端口**：`bridge.js` 依次试 `window.__API_BASE` → `backend_info` → 扫 5701~5717（跳过 5709）→ 默认 5701。

### 3.3 生命周期

| 时机 | 动作 |
| --- | --- |
| 双击 exe | `lib.rs::run()` **先** `spawn_backend()`（同步等端口，最多 45 秒），再 `tauri::Builder` 建窗口 —— 这样网页一加载就能连上 |
| 前端加载 | `bridge.js` → `loadHealth()` 拿 `confirm_token` → 连 `ws://…/ws/logs?from_start=1` → 派发 `pywebviewready`（`index.html` 的 `boot()` 就是等这个事件） |
| 首次启动 | `setup-wizard.js` 调 `/api/env/check`，缺件就弹向导 |
| 关窗 / 退出 | `on_window_event(CloseRequested)` 与 `RunEvent::ExitRequested` 都调 `stop_backend()` → Windows `taskkill /PID <pid> /T /F`（**必须杀树**），`-9` 兜底非 Windows |

**为什么一定要杀树**：`backend_server` 只是 FastAPI 壳，Agent 是它拉起的子进程，Agent 又拉起 NapCat。
只杀父进程会留下孤儿进程占着 5700/3001，下次启动全撞车。

###3.8知识图谱与自定义音色（V1.8.0）

**图谱是「增强」，不是「命脉」** ——这是这一节所有设计取舍的唯一依据。

```
memory.db（同一个库，不另开文件）
 ├─ perm_memory         一条条独立事实（老表，不动）
 ├─ kg_entities         user_id / name / norm / etype / mentions
 └─ kg_relations        subject / predicate / object / s_norm / p_norm / o_norm
                         confidence / source / perm_id / status
```

- 迁移靠 `PRAGMA user_version` 闸门（`kg.ensure_schema()`），**只加表不动数据**，任何异常 `return False`，
  绝不让图谱的问题把 `Memory()` 拖挂。
- 三个写入入口：`diary.PERM_PROMPT` 的 `triples` 字段（抽永久记忆时顺手入图）、`agent.kg_build_loop()`
  （默认每 1440 分钟补 20~50 条老记忆）、导入时整批 `kg.import_rows()`。
- 读：`agent.kg_block()` → `kg.context_block()`，默认 2 跳、上限 3 跳 / 4000 条边 / 14 行，
  拼进**易变段**——没命中就是空串，一个 token 都不占。
- 没有 `networkx` 时自动降级成邻接表（`_load_simple`），只是不保证最短路径。

**一个必须记住的教训**：「老板那只猫」这种问法，种子**不能只按实体名找**。
「老板」不是实体名，它是谓词「是…的老板」的一半。`seed_by_predicate()` 会把谓词切词块反查两端。
而且它必须跟 `find_seeds()` **合并**而不是「找不到才兜底」——否则命中「猫」之后就不再考虑谓词，整条链还是会丢。

自定义音色同理：`custom_voice → edge → sapi`，任何一步失败都 `except` 收进 `errors` 继续试下一个。
用户听不到「合成失败」，最多是「这次不是克隆的声音」，界面上会明确提示这一点。

细节见 `Docs\更新日志.md` 的 V1.8.0 一节与 `Docs\TECH_DOC.md` 的「V1.8.0 技术要点」。

**后端两个方法**（`app_ui.py` 的 `delete_perm` 之前，注册在 `av_tts_custom_test` 之后，`Api` 342 → **344**）：

| 方法 | 说明 |
| --- | --- |
| `kg_overview(user_id="", limit=120)` | 只读。返回 `{ok, user_id, entities, relations, networkx, edges[{subject,predicate,object,confidence}], hint}`；`limit` 夹 1~500；`_edges()` 按可信度降序取 |
| `kg_build_now(user_id="", limit=40)` | 当场织一批。`limit` 夹 1~50；返回 `{ok, scanned, added, skipped, msg, stats:{entities,relations}, user_id}` |

**为什么「立即补建」是同步的**：后台那条 `kg_build_loop()` 一天才跑一次（默认 1440 分钟），
用户点了按钮要马上看到结果，否则会以为没反应。一次最多 50 条，是「点下去不至于卡半分钟」和
「真能补上东西」之间的取中。

**为什么会话缓存**：`KG_DATA` 缓存住上一次的返回，切走再切回不重复请求（一个账号几千条关系时，
每次切页都请求一遍很浪费）。点「刷新」先把 `KG_DATA = null` 再拉。

**容错的三种说法**（都在界面上，不是 console）：

| 情况 | 用户看到 |
| --- | --- |
| 没装 networkx | 统计条后面追加 `⚠ 没装 networkx，只能看不能查`（列表照常显示，只是多跳检索用不了） |
| 一个关系都没有、但有永久记忆 | 「还没有关系。聊几轮让它抽，或者点『立即补建』把以前存下的永久记忆一次性织一遍。」 |
| 一个关系都没有、且没有永久记忆 | 「这个账号还没有永久记忆，图谱暂时没东西可织。」 |

**可信度配色**：`>=0.8` 绿、`>=0.5` 黄、其余红。同一句话被多次抽到会累加 `confidence`（每次 +0.1，上限 1.0），
所以绿的那批是「反复验证过的」。


###3.10无边框与标题栏（V1.8.2）

窗口顶部那条系统黑标题栏，根因**不在 `tauri.conf.json`**——那份配置里 `decorations`一直是 `false`。
真正的原因是配置文件里 `window_frameless`被历史版本写成了 `false`，于是一路把边框装回去：

```
config.json window_frameless=false
 → app_ui.get_status / win_state返回 frameless=false
 → bridge.js startup()调 applyFrameless(false)
 → invoke('set_decorations', {flag:true})
 → Rust lib.rs set_decorations(true) ←系统标题栏在这回来
 → body.frameless被摘掉，自绘条一起消失
```

所以要改的是一条链，不是一处：

|位置 |改了什么 |为什么必须改这里 |
| --- | --- | --- |
| `config.py`（`load()`里一次性迁移） |老配置 `window_frameless`不是 `true`就改回 `true`，同时写 `_frameless_migrated="1.8.2"` |没有标记的话，用户自己关掉无边框会被每次启动强改回来 |
| `app_ui.py`（4处默认值） | `bool(cfg.get("window_frameless", False))` →默认 `True` |和 `config.py`出厂默认对齐；读不到配置时不该退回有边框 |
| `bridge.js` `UI.frameless`初值 | `false` → `true` |任何一次状态没拿到都会走初值，初值错就等于默认有边框 |
| `bridge.js` `startup()` |不再 `applyFrameless(st0.frameless)`，先 `get_decorations`问窗口真实状态，再决定摘/不动/装 |「配置说无边框」和「窗口真的无边框」是两件事，混着用会把边框加回来 |
| `index.html` `renderStatus()` | `st.frameless`字段缺失时**保持现状**，只有拿到布尔值才动 DOM |后端还没起好时字段是 `undefined`，原来会走 else把自绘条摘掉 |

**标题栏**：三个按钮从 `—□✕`文本字符换成12×12内联 SVG描边图标，`cursor:pointer`、
hover上浮 `.5px` +底色、`:active`缩 `.94`、`:focus-visible`蓝描边；标题右侧一颗5px呼吸点
（`tbBreath`3.8s）；底线是居中对称的品牌渐变。

**最容易踩的坑**：最大化/还原图标用 `data-state="max"/"restore"` + CSS二选一显示，
所以 `textContent`那套必须**两处一起改** —— `index.html`的 `wireTitlebar()`和
`bridge.js`的 `syncMaxBtn()`。只改一处，另一处会把 SVG冲掉。

###3.11 Ollama为什么必须用 `LOCAL_KEYS`

底层早就支持 Ollama（`config.LOCAL_ENGINES = ("lmstudio","ollama")`），但 `PROVIDERS`里只有 `"local"`
（名字还叫「本地 LM Studio」），所以「按功能分工」的提供商下拉里看不到它。

补一个 `"ollama"`条目本身很简单，**难在8处 `== "local"`判据**：不改的话 Ollama会被判成「云端」——
于是一定要填 API Key、还会被 `api_enabled`过滤掉，用户填了半天也连不上。

所以新增 `LOCAL_KEYS = ("local", "ollama")`，把本地/云端判据全换成成员判断。
**注意 `kind == "local"`那几处不要动**：那是「优先级链项类型」，与提供商 key无关。

| `set_decorations` 这个 Rust 命令 | 设置页的「无边框」开关还要用它 |

**QQ 接管：为什么这次敢自动退 QQ**

同一句诉求在三个版本里被实现成三种样子（自动关 / 拒绝 / 再自动关）。这次的口径是「**只在用户亲手点的入口里接管**」，用代码结构保证，而不是靠注释约定：

| 入口 | 带 `takeover`？ |
|---|---|
| `start_napcat()`（「启动 NapCat」按钮） | 是 |
| `napcat_quit_qq_and_connect()` 的 `qq_client_busy` 分支 | 是 |
| `napcat_quit_qq_and_connect()` 末尾通用分支 | 是 |
| `napcat_login_state()` 的自动拉起 | **否** |
| Agent 子进程 `launch(wait=12)` | **否** |

`launch()` 里 `_take = bool(close_qq or takeover)`；`_take` 为真才 `quit_qq_client()`；老那条「检测到官方 QQ 在跑就拒绝」的守卫加了 `not _take` 条件，所以接管路径能穿过去。接管后复查 `qq_running()` 仍为真 → 明确返回「还有 QQ 进程没关掉」，不假装成功。

### 3.13 三条新交互线（V1.8.4）

**一、鼠标指针为什么只能用 PNG**

`cursor: url(...)` 里塞 SVG，Chrome 在 Windows 上**直接当无效值丢掉**、静默退回 `auto`（看起来就是「没生效」）。所以 `ui-cursor.css` 里的三张图都是 32×32 PNG 内嵌 base64（Pillow 画好再用超采样 + 高斯外发光）。

另一条硬规矩：**不做 `mousemove` 跟随特效**。`cursor` 属性是浏览器合成层直接画的，零成本；跟随粒子每帧都要跑 JS 布局，掉帧肉眼可见。

**二、自动保存为什么是「替用户点按钮」而不是自己拼参数**

设置页一张卡片里常有多颗保存键，且各自的参数不同（有的带 `restart`、有的要先校验）。如果自动保存自己组装 `save_settings` 的 payload，猜错就是**静默失效**：界面看起来存了，重启又变回去。所以 `sgAutoSave()` 查 `SG_AUTO` 表拿到那颗按钮的 id，直接 `.click()`，走原来验过的那条路。

没进 `SG_AUTO` 表的卡片，只有在**卡里没有文本框**时才敢用「卡里唯一那颗保存键」兜底。

「放弃修改」= 恢复 `focus` 时记下的原值 + 清脏标记，**不写盘**。

**三、多账号隔离的三个易错点**

1. **切账号必须先清缓存**：`lastOverview = null`、`KG_DATA = null`、`lastMsgs = []`，否则切过去的一瞬间会短暂显示上一个账号的数据。
2. **群聊不按账号归属**：`get_memory_data(user_id=)` 只查 `private_<uid>` 这一条会话，群聊消息不混进来（没法归属）。
3. **`kg_overview` 只在「关系网」子页激活时才拉**（`renderGraph()` 里 `if (KG_DATA) 复用 else loadGraphData()`）。只验证首屏「切账号是否带参数」会误判它没接上账号。

**四、napcat_proc 的识别判据（比字面要求更严）**

原始要求是「命令行含 `napcat` / `index.js` / `napcat.mjs` 即算」。实测本机有一条 `node.exe ...\.dsh\...\billion-context\dist\index.js`（开发工具），按字面实现会**把用户正在用的进程杀掉**。收紧成：命令行含 `napcat` / exe 在 `runtime/napcat` 下 / 命令行走的是我们记录的 NapCat 目录。**光有 `index.js` 不算。**

防孤儿靠 Job Object：`_JOB_LIMIT_KILL_ON_JOB_CLOSE = 0x00002000`，`_spawn()` 里每起一个 node 就 `attach_job`。主程序被强杀，内核替我们回收。

### 3.15 排版预设为什么必须用 DOM 顺序（V1.8.6）

V1.8.5 的修法（后端把 `ui_card_order` 的列表值保留下来）只解决「存不住」，没解决「存错了」。真正的坑在浏览器布局：

- 设置页每栏都是 `flex flex-col` 容器。flex 排序时 **CSS `order` 优先于 DOM 顺序**，所以只要卡片带 `style.order`，`insertBefore` 搬 DOM 视觉上一点反应都没有 —— 用户以为拖好了，其实没动。
- `collectCardOrder()` 又按 `style.order` 排序，于是「存预设」存下来的是拖动前的旧排列。
- 应用预设只改 `style.order`，视口顶部那张卡被排到末尾时，Chrome 的**滚动锚定**会把视口一起拽到底部。

三条规矩，以后改这块别再破：

1. **卡片顺序只认 DOM**（`insertBefore` / `appendChild`），不要再用 `style.order` 排卡片；
2. 读顺序一律 `_layoutCards(sec)` 扫子节点，不要读样式；
3. 任何会重排大量子节点的操作，前后都要保 `scrollTop`，并临时 `overflow-anchor: none`。


### 3.16 增量包为什么必须用 payload/ 隔一层（V1.8.6）

QA 终审判 No-Go 的理由很实在：**包结构本身就不安全**。旧增量包把所有文件摊在 zip 根目录，
跟 `apply_delta.ps1` 平级 —— 用户按常理「解压到程序目录」，Windows 的解压就是直接覆盖，
脚本一行都还没跑，程序已经被写坏了。校验做得再严也没用，因为**校验发生在覆盖之后**。

现在的分工：

| 层 | 放什么 | 谁保证安全 |
| --- | --- | --- |
| `payload/` | 真正要替换的文件（只有新增和改动过的） | 路径合法性 + 逐文件 sha256 对清单 |
| 包根 `delta_manifest.json` | 清单（`kind` / `from_version` / `to_version` / `files[]` / `remove[]`） | ps1 先读它，读不出就 exit 2 |
| 包根 `apply_delta.ps1` | 校验 → 备份 → 替换 → 复核 | 失败一律红字 + 零改动 |
| 包根 `应用增量包.bat` | 双击入口（`chcp 65001` + `-ExecutionPolicy Bypass`） | 中文不炸码页 |
| 包根 `README.md` | 用法 + 退出码表 | 用户不用翻文档 |

四条不该破的规矩：

1. **先校验后动手**：`payload/` 里任何一个文件哈希对不上，直接 `exit 4`，目标目录一个字节都不碰；
2. **先备份后覆盖**：全对之后才把「将被覆盖/将被删除」的文件复制进 `<程序目录>\_backup\pkg-<时间戳>\`，
   并在同一目录写 `restore.ps1`（递归回写 + 按 `added.txt` 删新增）—— 回滚不靠用户记步骤；
3. **复制完再复核**：替换后再算一遍哈希，不符 `exit 7` 并让用户跑 `restore.ps1`；
4. **源=目标要认出来**：`$Target` 等于 `payload/`、或在其内部 → `exit 5`；
   `$Target` 是 `payload/` 的父目录（即用户把包解压进了程序目录）→ 黄字提醒但照常更新，不死循环。

`updater.apply_package()` 那边补了一道反向闸门：看到 `kind == "release-delta"` 就拒绝，
提示改用「解压后双击 `应用增量包.bat`」。否则程序内更新会按源码白名单把 `payload/xxx` 写进数据目录 ——
程序不但没升级，还多了个没用的目录。


### 3.17 启动探活：别拿「体检」当「心跳」（V1.8.7）

V1.8.6 出了一个致命 P0：**干净机器上第一次打开永远白屏**。链条是这样的：

| 环节 | 做了什么 | 为什么出事 |
|---|---|---|
| 壳子等问题 | `health_ok(base, 900)`，`for _ in 0..20` | 总预算 18 秒，看起来很长 |
| 敲的接口 | `GET /api/health` | 这个接口要探 NapCat(0.6s×2)、edge-tts、Node(`-v` 最多 8s) |
| 干净机器 | 三项全是「没装」 | 前两项各要 1.2s，合计 1580~2000ms |
| 结果 | 每次都超过 900ms → `kill_tree` → 重试 3 次 → 弹框 | 健康的后端被杀了三次 |

**规矩：心跳接口只有一个职责——回一句「我在」。** 它不许碰任何外部进程、不许读文件、不许发网络请求。
`/api/health` 是体检报告，是给「设置 → 环境检查」看的，慢一点没关系，但不能当心跳用。

现在 `health_ok()` 敲 `/api/ping`（只回 `{"ok":true,"pong":true,"ts":...}`，实测 5~9ms），
`SPAWN_PING_MS = 5000`、`SPAWN_PING_TRIES = 10`。

顺带把 `/api/health` 自己也治了（因为它还有别的调用方）：

| 手法 | 位置 | 关键点 |
|---|---|---|
| 后台预热 | `_health_warmer()` + `start_health_warmer()`（`main()` 里起 daemon 线程） | 每 45 秒刷一次，接口只读缓存（`_HEALTH_TTL = 60.0`） |
| **冷启动也不阻塞** | `_health_plugins()` 缓存空时 `return {}` + 起 `_cold()` 线程 | 这是全篇最容易做错的一步：先给空，前端显示「检测中…」，几秒后自动变真值 |
| 探测本身提速 | `napcat_mgr.probe(deep=True, timeout=0.1)`、`_node_status()` `timeout=2.5` | 127.0.0.1 上 0.1s 完全够 |

**例外，别一起改了**：`/api/env/check` 里的那份 plugins **必须现查**——那是用户主动点的「查缺什么」，给缓存就是骗人。

另外 `lib.rs` 加了 `last_boot_error()`：启动失败时从 `boot.err.log` 读最后一条非空行塞进原生错误框。
以前只写三条通用原因（杀毒/端口/更新包），用户根本不知道是哪条——这等于没报错。



### 3.18 为什么「0」和「没填」必须分开判断（V1.8.8）

| 写法 | 用户设成 0 会怎样 | 结论 |
|---|---|---|
| `int(cfg.get("k") or 25)` | 读回来还是 25 | **错**，`0` 被当假值 |
| `int(cfg.get("k") if cfg.get("k") is not None else 25)` | 正确 | 啰嗦，32 处会写吐 |
| `_ndef(cfg.get("k"), 25)` | 正确 | 现在的统一写法 |

`_ndef` 放在 `app_ui.py` / `agent.py` / `token_est.py` / `diary.py` / `subconscious.py` /
`usage.py` / `mem_transfer.py` 各一份（这些文件互相不 import，宁可重复也别耦合）。
判定规则只有两条：`None` 和「全是空白的字符串」才回落默认，`0` / `0.0` / `False` 原样保留。

改之前先确认「设成 0 有没有意义」——`max_tokens`、`web_port`、`affinity_max` 这类设 0
就是错的，必须留在原写法，所以有个 44 个键的 `LEGIT_ZERO` 白名单。

### 3.19 主题 / 特效 / 字号的联动状态机（V1.8.8）

四个真因，缺一条都还是会打架：

1. **渲染读「缓存有没有」而不是「真值有没有」** → 切主题时缓存还没填，传空对象把
   `--ui-font` 摘掉，字体回默认；再进设置页又装回来。现在渲染只读 `_store()`，
   且 `_store()` 保证结构完整、永不为 null。
2. **两套来源混用** → 主题自带 effects 和用户设置各写一遍，谁后写算谁的。现在优先级
   统一在 `fxEffective()` 里算一次：用户 > 上次落盘 > 主题自带 > 出厂。
3. **`false` / `''` 被当成「没设置」** → 用户显式关掉雪效，切主题又被主题的 `true` 顶开。
   现在只有 `null`/`undefined` 代表没选过；`bg_effect === ''` 明确表示「跟随主题」。
4. **没有序号** → 先发的响应后到，覆盖后点的。现在三个写入通道各带自增 `_seq*`，
   响应回来若自己不是最新一次就整包丢弃（last-click-wins）。

三条规矩，以后改外观相关代码都要守：

- 想改外观 → 只能走 `commitTheme` / `commitFx` / `commitLook` / `resetLook`，
  **不要直接写 `document.body.style` 或 `dataset`**（除了这三个函数内部）。
- 想画界面 → 只能读 `_store()`，**不要读 DOM 反推状态**。
- 新增外观字段 → 同时加进 `LOOK_FACTORY`/`FX_FACTORY` 和 `LOOK_CFG_KEY`/`FX_CFG_KEY`
  （前者是出厂值，后者是落盘键名），否则「恢复默认」会漏掉它。

### 3.20 预设为什么必须用 data-card-id + 物理重排（V1.8.9）

V1.8.6 已经让 `applyCardOrder` 物理重排 DOM，但**卡片身份**还靠「`sec.id` + 标题 slug」，标题一改
就整体错位；而 `collectCardOrder()` 那会儿读的是 DOM 顺序（对的），可拖拽结束后 `saveCardOrder()`
存的是「拖完的顺序」—— 一旦某张卡的标题变过，预设里的 key 就再也匹配不上，表现就是「存了新的 =
和旧的完全一样，点了应用画面不动」。

这一版把身份钉死：

| 层 | 规则 |
|---|---|
| HTML | 每张设置卡片必须有 `data-card-id`，**全局唯一、永不改**（`card-look`、`card-settings-01`…） |
| 采集 | `collectCardOrder()` 只读 DOM 顺序，取 `data-card-id` 数组 |
| 应用 | `applyCardOrder()`：`removeChild` 全摘 → 按数组 `insertBefore` 插回；缺 id 的 `out.concat(pool)` 追加末尾 |
| 兼容 | 老预设里的标题碎片仍用 `_slugKey()` 兜底匹配一次，匹配不上就当新增卡片放末尾 |

滚动这条必须一起处理，否则「重排对了但页面被甩到页底」，用户一样认为没修好：

- 重排前 `sec.style.overflowAnchor = 'none'`（关掉 Chrome 滚动锚定），排完 rAF 里恢复；
- `scrollTop` 无条件写回原值（含 0），rAF 里再写一次；
- 重排前 `blur()` 掉容器内的 `document.activeElement` —— 否则浏览器为「保住焦点」把视口拽到被搬走的卡片那儿。

以后要动这块，三条不能破：**①卡片身份只能用 `data-card-id`；②顺序只认 DOM，不写 `style.order`；
③重排必须包在「关锚定 + 存回 scrollTop + blur」这三件套里。**

### 3.21 三条「看不见的手」（V1.8.10）

**一、`isSettingsLoaded` 闸门 —— 一次异常，永久静音**

`loadSettings()` 把 `isSettingsLoaded` 设 false，末尾才设 true。中间 `loadUninstall(); await loadNapcat();`
这两句**没包在 try 里**，探活超时就抛 → 末尾那句不执行 → 之后每次 `save_settings` 都被 `call()` 的闸门
`return { ok:false, msg:'settings loading' }` 静默拦掉，而界面还弹「已保存」。

**规矩**：凡是「进函数先关闸、出函数开闸」的写法，一律 `try/finally`；闸门本身也要有超时兜底
（现在最多等 4 秒就放行 + `console.warn`），绝不能把用户永久锁死。

**二、预设为什么还要留一份 localStorage 镜像**

服务端 `ui_layout_presets` 本来没问题（`config.set_checked` 有专支，dict 原样存、最多 10 套）。
加镜像是为了「前端已经存了、服务端那次请求恰好失败」这种半成功状态：`applyPreset` 内存里找不到就回落镜像，
`__applyLayoutFromSettings` 用镜像补齐缺的。**镜像只是兜底，永远以服务端为准**。

**三、`bridge.js` 的 base 不能永久缓存**

`resolveBase()` 以前 `if (base) return base`，而 `backend_info` 返回的 `state.base` 是**启动时**的端口。
后端重启换端口后前端指死空号。现在的三层自愈：①地址先探活；②请求失败重找 + 重试 3 次；③20 秒心跳，
连续 2 次不通就重找。**任何「拿到就缓存」的地址/句柄，都要配一个失效条件。**

**四、追问的登记点为什么放在 `send_to_session()`**

那是所有出站消息的唯一总闸（私聊/群聊都过它），放这里才记得住「机器人问过什么」；
清零点放在 `process_message()` 的 `_note_user_text()` 之后（收到对方任何消息就清）。
追问自己发出的消息要打 `_FOLLOWUP_INTERNAL` 标记，否则会「追问→登记→再追问」自激。


### 3.22 三个「假功能」的共同点（V1.8.11）

这三件事坏得不一样，但根子是同一类：**开关和状态都在，接线断了，而代码不喊**。

1. **预设存不上** —— `loadSettings()` 里一句没被 try 包住的 `await loadNapcat()` 抛异常，
   `isSettingsLoaded` 就永远停在 `false`；`call()` 的闸门于是把**所有** `save_settings` 悄悄丢掉。
   教训：**任何「加载中」开关都必须 try/finally**，而且闸门要有超时兜底（这次给 4 秒），
   宁可放行让后端报错，也别静默吞。
2. **追问不触发** —— 登记函数 `followup_mark()` 只挂在 `send_to_session()` 上，
   而日常回复十几处都直调更底层的 `send_private_human` / `send_group_human`。
   教训：**要钩住「所有发出的消息」，就得钩最底层那个出口**，不能钩在某条上层分支上。
   顺便记住要防自激：自己发出去的追问不能再登记成新的「等回话」。
3. **主动关心不触发** —— 计划完全依赖模型从聊天里抽 `care`，抽不到就永远安静。
   教训：**给「靠模型抽」的路径配一条不依赖模型的兜底**（这里是「静默超过 N 小时就说一句」），
   否则模型一旦不配合，整条功能就是零。

另外两处「读不到就一直显示 —」：请求队列打了一个**从来不存在的路由**，
数据库读了一个**不存在的属性**。教训：跨进程共享的数据要么走文件、要么走真实接口，
写代码时别假设「应该有」。

### 3.23 「功能写完了」和「功能真的会跑」差一次调用（V1.8.12）

这一版最典型的教训，是 `pq_state()`：函数写得漂漂亮亮、落盘逻辑也对，但**没有任何地方调用它**。
表现就是控制台那一格永远「—」，而代码看着完全没问题。三条经验：

1. **写完落盘/上报函数，顺手在唯一的入口调用它**（这里是 `_pq_enter`/`_pq_exit`），
   并用「读端能拿到非空数据」当验收标准，而不是「文件里写了这个函数」。
2. **降级链要能自己证明跑过**：真唱的三档（云端→SVC→朗读）用「云端返回 500 时必须 still 出音频、
   且 note 里说明退回到哪一档」来测，光测成功路径等于没测。
3. **同一份状态不要有两条写入路径**：表情包开关的「回跳」就是 `SG_AUTO` 和 change 处理器
   同时写一个下拉造成的。要么即时保存层别管它，要么 change 处理器不碰它。

另外两条本版新增的硬规矩：

- **按秒存时间，按单位显示**：`care_idle_silence_sec` 是唯一真源，前端算 `v * 60/3600/86400`。
  迁移标记必须登记进 `DEFAULTS`（`_care_idle_unit_migrated`），否则 `save()` 只保留已知键 = 标记白写。
- **情绪判定要能解释**：本地判「否认情绪」时不要把整句丢掉，要单独给一个情绪名，
  否则「我不难过」会被当成「没有情绪」。

### 3.24 位置传参的隐式契约，和「正则抠 HTML」的两种死法（V1.8.13）

**一、位置传参是最脆的耦合。**
`Api.save_emotion_center` 一直写 `save_emotion_center(preset, enabled, timeout, prompt_text)`。
这种写法在形参顺序不变时完全没问题，可一旦签名改动（哪怕只是少了一个参数），调用不会报错 ——
它会安静地整体错位，然后在你根本没想到的那一行炸 `NameError`。
**硬规矩**：跨层调用（`Api` → 模块级函数）一律关键字传参。省下的那几个字符，不值得一次整页功能失效。

**二、正则抠 HTML 有两个坑。**
1. **非贪婪只吃第一个子元素**：`<(div) class="lyric-content">(.*?)</p>` 会在第一个 `</p>` 处收尾，
   于是只拿到第一句歌词。要么用 `HTMLParser` 按标签深度收，要么老老实实写配对逻辑。
2. **退回整页文本会混进噪声**：`<title>`、导航、版权声明全在里面，
   `parse_lyrics` 只能靠长度和关键词过滤，很容易把「稻香 歌词」当成一行歌词。
**硬规矩**：抓页面时优先按语义区块收；收不到再退整页，且必须对结果做行数与内容双重校验。

**三、「没变化」和「改不动」必须能区分。**
`applyCardOrder` 找不到任何目标卡片时，DOM 确实没变化，于是老提示说「和当前顺序一样」——
用户看到的是「你说成功但什么都没动」。任何「应用某套配置」的操作，都要先统计**命中率**，
命中 0 时单独给一条明确的失败提示。

### 3.25 「浏览器已经改过了」——三处假死其实是同一个时序问题（V1.8.14）

三个 P1 摊开看，根子是同一件事：**代码假设的时序，和浏览器真实的时序不一样**。

1. **checkbox 的 click 里，`checked` 已经是新值了。** 所以 `const on = !swGet(id)` 永远等于旧值，
   存下去的还是旧状态 —— 开关看着像假死。正确写法是直接读 `el.checked`（INPUT）或自己算
   `classList`（div 开关），也就是 `swNext(id)`。这个坑 V1.8.8 踩过一次，V1.8.14 又踩，
   所以自测里加了「内联脚本不允许出现 `!swGet(`」这条硬断言 —— 靠人记不如靠测试拦。
2. **`select` 的 change 里直接重载，等于把用户刚做的选择丢掉。** 正确顺序是：先落库 →
   成功后再刷新 → 刷新前先把界面上的反馈（徽标/文案）改掉，让用户立刻看到结果。
3. **兜底比不兜底更危险。** 抓不到歌词区块就整页去标签，结果把「客户端 下载 登录」喂给 TTS。
   现在改成：抠不到就返回空，让上层说「没搜到」。**宁可功能不работать，也不能输出错的东西** ——
   错的输出用户会当成 bug，空的输出用户知道是没找到。

两条可复用的规矩：

- **凡是「点了没反应」的 bug，先问一句：事件触发时，DOM 里的值到底是新的还是旧的？**
- **凡是「兜底逻辑」，都要问一句：兜底出来的东西，最坏情况会是什么？** 如果最坏情况是
  「把无关内容当结果」，那就不该有这条兜底。

### 3.26 「宁可功能不работ，也不能输出错的东西」（V1.8.15）

这一版的教训只有一句：**兜底逻辑的输出，会被用户当成"功能"**。

- 拿搜索结果标题当歌词 → 用户听到「稻香 - 完整版歌词 - 百度文库」，会认为"她坏了"。
- 搜索失败时把返回体当文本 → 用户听到报错原文，会认为"她疯了"。

两次都是"想让功能看起来能用"，结果比直接说"没搜到"糟得多。所以这一版把
四道闸全装上，且**最后一道闸是"凑不够 5 行就返回空"** —— 主动放弃，
比输出垃圾强。

顺带两条：

- **配置键要看语义，不要看名字像不像。** `web_enabled` 是网页版服务，
  `agent_web` 才是"Agent 能不能联网"。名字像就拿来用，用户会看到
  "开关开着却被拦"这种自相矛盾的行为。
- **只存在内存里的 UI 状态，等于没有状态。** 开关的默认值不要硬写，
  要从配置读、改动就落盘。

### 3.27 「存了但没存全」和「打了但没打进去」（V1.8.16）

这一版的两个 bug 都不是逻辑写错，而是**链路两头没接上**，而且都能用一句话说清：

| 现象 | 真因 | 教训 |
|---|---|---|
| 应用预设只有卡片动 | `collectCardOrder()` 只返回卡片 id 数组，预设里**从来没有主题和特效字段** | 一个「保存/应用」功能，先问「保存的到底是完整状态吗」；只存了一半，应用端再努力也没用 |
| 切英文只有顶栏变 | `langs/` 没进 PyInstaller 包；`ensure_dir()` 用一份没有 `ui` 段的样例兜底；前端 `if (!n) return;` 静默跳过 | **兜底数据必须和真实数据同构**。兜底缺了 `ui` 段，就等于「永远没有译文」，而且一声不响 |
| 长段说明永远不翻 | `_uiWalk()` 用 `raw.trim()` 精确匹配，而文本节点里带着 HTML 的换行与缩进 | 拿 DOM 文本去查表，一律先折叠空白；「查不到」要能定位，不能静默 |

两条硬规矩（写进流程）：

1. **打包后必须验证「文件真的在包里」**：`langs/`、`av_module/`、`napcat_bundle.zip` 这类
   外部资源，`--add-data` 漏一行就整块功能消失，而且本地跑源码永远是对的。
2. **静默降级要留痕**：`applyUiLang()` 拿到空词表就 `return`，是这个 bug 藏了两版的原因。
   现在 `get_ui_lang` 会明确返回 `ok:False` 和原因。

### 3.28 安全改造里最容易「装上了但其实没生效」的四处（V1.9.0）

这一版全是安全项，而安全项的通病是：**代码写了、测试绿了、实际没生效**。四处都踩到了，
记下来给下次：

| 表面现象 | 真正原因 | 怎么才叫真生效 |
|---|---|---|
| 胶囊导出没提示设口令 | `_open_capsule()` 只认 v2 魔数，v3 直接走「损坏」分支 | 必须拿真文件走一遍「导出 → 换台机器导入 → 口令错一次」 |
| Token 加了但还是能改配置 | `_token_guard` 只在用户手动设环境变量时才校验，默认等于没开 | 起真后端，**不带 Token 发一次 POST**，必须拿到 401 |
| 签名文件在包里但没人验 | `sign_zip()` 只写文件，`get_status()` 没调 `verify()` | 手动改包里一个字节，重启必须弹拦截层 |
| `.pyd` 打了但源码还在 | 只加 `--add-binary`、没加 `--exclude-module`，PyInstaller 仍把 `.py` 塞进 PYZ | 解包后在 `_internal` 里搜 `def encrypt_with_password` 必须搜不到 |

两条硬规矩：

1. **安全项必须有一条「反着来」的用例** —— 不是「正确时能过」，而是「错误时必须被拦住」。
   上面四项的自测里，每一项都配了一条「故意不带凭证」的负例。
2. **Cython 的产物要去掉 ABI 标签**（`audit.pyd`，不是 `audit.cp311-win_amd64.pyd`），
   否则冻结后 `import audit` 找不到，而源码已被 `--exclude-module` 排除，程序直接起不来。

### 3.29 「装上了」和「跑起来了」差一次真实路径（V1.9.1）

V1.9.0 的四个安全模块，代码全对、自测全绿，但复测报告一句话全否了：**装甲没穿到身上**。
根子都是同一件事 —— 只在「我以为的路径」上验证过。

| 以为 | 实际 | 后果 |
|---|---|---|
| 清单在包根，`verify_program_dir()` 去包根找 | 冻结版 `sys.executable` 是 `<安装目录>\resources\backend_server.exe` | 永远找不到清单，**签名一次没跑过** |
| 找不到清单 = 自己编译的 = 放行 | 攻击者只要**删两个文件** | 整套校验成本 = 删两个文件 |
| `status()` 写 `ok: True` 是「摘要」 | `verify()` 的失败被一把丢掉 | 前端只看 `tampered`，照常启动 |
| Python 里验签就够了 | Python 代码本身就在被校验的包里 | 验证器和被验证对象一起被换掉 |
| Cython 编译 = 藏住密钥 | `.pyd` 的 `.rdata` 里 base64 分片明文可见 | 一次编译，密钥永远一样 |

两条硬规矩：

1. **安全项必须有一个「反着来」的负例**：删清单、改一个字节、换私钥、伪造清单，
   每一种都要有一条断言证明「被拦住了」。只证明「正常包能过」等于没测。
2. **安全逻辑要放在攻击者改不动的那一层**：验签放外壳（Rust）、门禁放后端中间件、
   密钥放打包期生成 —— 不要放在「用户能改、攻击者也能改」的同一层。

### 3.30 「验过了」不等于「启动的是它」（V1.9.2）

安全改造最容易犯的错，是把「校验」和「使用」当成一件事。V1.9.2 修的四个洞里有三个都是这个形状：

| 以为 | 实际 |
|---|---|
| 清单里有 `backend_server.exe`，外壳验过就安全了 | 外壳按自己的规则找文件，清单里那个只是「之一」—— 换掉安装目录里那个就绕过 |
| 增量包用包里的新后端验签，说明包是官方发的 | 包和验签程序都是攻击者给的，这叫自证循环 |
| 把密钥写进 `.py` 再编译成 `.pyc`，等于藏起来了 | `marshal` 一读就是明文；`.pyd` 的 `.rdata` 里字符串照样可搜 |

两条硬规矩：

1. **校验通过的路径必须一路用到最后**：`verify_release()` 现在返回那份 `canonicalize` 过的
   `PathBuf`，`spawn_backend_once()` 拿它跟 `cmd.get_program()` 比，不一致直接拒绝启动。
2. **拿别人的东西验证别人，不算验证**：增量包只能用「本机已装的、被外壳验过的主程序」验签。

另外一条界面侧的：`<style>` 的胜负靠**文档顺序**，不靠 `!important` —— 变量样式挂在
`<head>` 而主题静态样式在 `<body>` 里时，后者永远赢。要么加优先级，要么挪到 body 末尾。

### 3.31 「密钥藏不住」和「假装藏住」（V1.9.3）

上一版把 SECRET 编进 `.pyd` 之后，安全团队用一条正则 0.5 秒就拿走了。这一版换了思路：

| 旧 | 新 | 为什么 |
|---|---|---|
| 32 字节种子 base64 成常量编进 pyd | 构建期直接算出「盐」和「清单密钥」，切成 8 片、每片异或后写成元组 | 泄露的只是盐，不是种子；没有种子就推不出下一个版本的盐 |
| 源码里 `_BUILD_SECRET_B64 = ""` 占位，构建期填值 | 删掉整个种子链路；源码里只有 `_SHARDS_SALT = ()` 占位 | 「程序里没有整串钥匙」是可以被 grep 验证的，不是口头承诺 |
| 无诱饵 | 4 条 43 字符假 base64 + 4 个陷阱环境变量 → 假盐 | 想用正则扫的人会扫到一堆假货，拿去用只会得到乱码 |
| 自检只看「向上有没有清单」 | 必须能在清单里找到**正在运行的自己** | 借父目录清单蒙混，是最容易被忽视的一种「合法」伪装 |

三条硬规矩：

1. **诱饵必须能被扫到才算数。** Cython `binding: True` 会把长字符串按 8 字符切开、模块级常量还会被折进常量表，
   所以诱饵要写成函数体里的 `return b"..."`，并在编译输入第一行加 `# cython: binding=False`。
   验证方法是拿正则去扫 pyd 字节，数得出来才叫诱饵。
2. **兼容旧数据靠的是「旧值还在」，不是「旧算法还能跑」。** 轮换密钥时同时提供
   `*_legacy()` 返回旧值列表，按「新 → 上一版 → 历史」逐个试；只换算法不留旧值，等于让用户全部重设口令。
3. **开关的签名要跟着开关一起存。** 签名不登记进 `DEFAULTS` 就永远写不进盘（`save()` 只保留已知键），
   而校验失败必须选一个安全默认值 —— 这里是「全部强制开启」，不是「保持原样」。


### 3.32 「会失败」比「失败了怎么办」更难想到（V1.9.4）

V1.9.3 的安全做得比以前都硬，但 QA 一用就发现：**最伤用户的不是被破解，是升级装到一半变砖**。
`apply_delta.ps1` 原来是逐个文件复制 —— 第三个文件被杀软拦一下，目录就一半新一半旧，
主程序和后端版本对不上，双击起不来。这不是安全问题，是「失败路径没设计」的问题。

三条硬规矩：

| 规矩 | 为什么 |
|---|---|
| 换文件必须「先备齐、再一次换」 | 逐个复制等于把失败点乘上文件数；`Move-Item` 同盘 rename 是单个文件原子 |
| 任何一步失败都要能回到起点 | 备份要在**换之前**做、回滚判定以哈希为准（不信"看起来回来了"） |
| 弹窗必须有超时 | `Popup(…, 0, …)` 是永久等待，无人值守的机器会挂在那里 |

另外两条同类教训：

- **签名校验必须 fail-closed**：`verify()` 缺 `manifest.sig` 时只把 `signed` 设 False 却继续比对哈希，
  等于「删掉签名就没人管」。这个洞修了三次才彻底关掉 —— 修的时候别只看 `if` 分支，要看「没有那个文件」会走到哪。
- **能改状态的东西不能只靠一个函数自觉**：`config.save()` 对任何值盖章，于是任何能调 `save_settings` 的路径都能关掉防护。
  改成「`save()` 默认退回 + 只有 `guard_apply()` 能改 + 改就写审计」，才不依赖调用方守规矩。

### 3.34 「我验过了」要跟着「我验的是哪一份」（V1.9.6）

V1.9.5 加了一条硬检查：正在运行的程序必须在安装包的清单里。逻辑没错，但它默认了
「安装包的清单包含主程序」——安装包只对 `resources/` 下三个文件签名，主程序压根不在里面。
结果每个用安装包的人第一次打开都被判篡改。

| 想当然 | 实际 |
|---|---|
| 清单就是整个安装目录的清单 | 安装包的清单只覆盖 `resources/` 三个文件 |
| 找到清单就能验 | 目录里可能同时躺着两份清单，碰到哪份看运气 |
| 验不过就是被改了 | 也可能只是「这份清单本来就不管这个文件」 |

两条硬规矩：

1. **一份清单管哪些文件，是清单自己说了算**，别假设它覆盖整个目录。
2. **同名校验文件可能有多份**，要么全试一遍（任一能过即过），要么先把它们收敛成一份。

同一类教训在 V1.9.2 也出现过一次：那次是「验过的路径」和「启动的路径」不是同一个。
两次都证明：**校验的输入不止是数据，还有「这份数据负责的范围」**。

### 3.33 「代码在」和「代码会跑」是两件事（V1.9.5）

| 症状 | 真因 | 硬规矩 |
|---|---|---|
| 沙箱拦截写了但从来不生效 | 四行被插在 `_bind_args()` 的 `return` 之后，语法合法、永不执行 | 插入防御代码后**必须构造能触发的用例**跑一遍，不能只看 `py_compile`；插入锚点要选在目标函数体内，插完 `print` 一下函数源码确认位置 |
| 防护章能被一行文件改动骗过去 | `_guard_key()` 对 `raw:` 前缀照单全收 | 「用户可写的文件」里的密钥**一律不采信**，只能当「被改过」的物证；密钥优先 DPAPI，拿不到就只放内存 |
| 换锁检测有代码但不触发 | `_guard_check()` 先判标记、后调 `_guard_key()`，标记那时还是空的 | 检测顺序本身是逻辑，**先制造条件再判断**；用「三步真机脚本」验证（生成→篡改→重启） |
| 旧密钥表 0.238 秒被取走 | 4 条 base64 存成模块常量 + 导出 `keys()/pick()` | 想让扫描器扫不到的东西**不要以文本常量存在**；不要再导出取用函数（等于把 API 送给对方） |
| 主程序拷到子目录可以通过校验 | `verify_release()` 只核清单文件，不核「自己」 | 「验过的」和「正在跑的」必须是同一个路径，两侧（Python / Rust）都要有 |

### 3.36 自己产生的东西，自己得认得出来（V1.9.9）

| 事故 | 现象 | 根因一句话 |
|---|---|---|
| 说说评论套娃 | 她回自己的评论，一轮接一轮 | 读回来的评论分不清是谁发的，去重键里 `commenter_id` 是空 |
| 「四点叫我」不叫 | 明确要求被当普通闲聊 | 静默门槛只看「最近有没有聊过」，不看是不是祈使句 |
| 改说明就报篡改 | 换一张图启动被拦 | 清单把说明书、图片也算进了「程序本体」 |

**两条硬规矩**：

1. **凡是自己写出去的东西，回读时必须有「这是我的」判据**（uin / 昵称 / `direction` 三者至少要有一个可靠）。只靠内容去重不够 —— 同一条内容可能是别人说的，也可能是我自己说的。
2. **礼貌性的抑制规则（静默、冷却、随机跳过）不能盖过用户的明确指令**。祈使句要能被识别出来，并且有一条直达通道。


### 3.45 「代码在猜意图」和「模型在判断意图」是两件事（V1.9.15）

用户反馈「人机味极重」，拆开是三个不同的毛病，根子却是同一条：**程序在用字符串代替理解**。

1. **抢动作**：`process_message` 里 `if is_self_draw(text): 画` / `if is_avatar_change(text): 回台词`。
   字符串命中就抢走整轮回复，所以「你看这个」能触发画图。
   改成 `CHAT_TOOLS` + `_chat_with_tools()`：模型自己决定要不要调工具，程序只执行。
2. **自省没上文**：`post_reflect_apology` 只拿到 `raw_text` 和 `reply`，历史一条没给，
   模型只能硬编 —— 于是「是程序啦…中午刚吃过大白饭」。改成 `_reflect_context()` 取最近三轮，
   并且允许它输出 `SKIP`（觉得没问题就不发）。
3. **客服腔**：固定台词 + 固定句式。除了删台词，还得在提示层写死：
   不许硬拼记忆碎片、不许附和式开场、想不出就少说两句。

三条硬规矩（以后加功能都照这个来）：

- **凡是「意图」，一律交给模型判断，代码只做执行**；代码里出现「如果出现某个词就做某个动作」，
  一律视为待拆。
- **凡是让模型「评价/补话/反思」，必须把它当时能看到的东西原样喂进去**，否则它只能编。
- **兜底台词只留给系统级失败**（模型/网络彻底不通），正常对话不许有写死的句子。

### 6.2 打包/进程类

| 坑 | 现象 | 解法 |
| --- | --- | --- |
| PyInstaller onefile 是两个进程 | 只杀父 PID，端口还被占着 | `taskkill /PID <pid> /T /F` 或按名字杀 |
| `tauri build` 报 resource 不存在 | `resources\backend_server.exe doesn't exist` | 先跑 `python build_backend.py`（这是故意的检查） |
| Rust 拿不到 `state` | `no method named state` | `use tauri::Manager;` |
| 管道不读会卡死后端 | 后端跑一会儿不动了 | stdout/stderr 各起一条线程抽干 |
| CORS + 危险接口 | 任意网页能 POST 到 127.0.0.1 | 白名单 origin + `X-Confirm-Action` 令牌（见 TECH_DOC 第 5 节） |
| frozen 版 pip 等于没装 | 向导说「装完了」，重启还是未安装 | 依赖要**内置进 exe**（`ensure_edge_tts()` + `--hidden-import`），或在打包版的检测里明确说「需重新打包」 |
| 首次启动防火墙弹窗写「Python」 | 小白不敢点「允许」 | `build_backend.py` 的 `write_version_file()` 给 exe 加版本信息，弹窗显示「小鲸鱼 Agent 后端服务」 |
| **端口被自己人抢** | Agent 一启动就「已有另一个 Agent 在运行」，点几次都一样 | 单实例锁端口别挑后端会用的段：后端占 5701（5700 留给 webhook），锁改成 **5709** 并加进 `RESERVED_PORTS` |
| **懒 import 的库没打进包** | 打包版 Agent 秒崩，`agent_crash.log` 写 `No module named 'requests'`；源码模式却全好 | `build_backend.py` 的 `LAZY` 清单把函数内 import 的模块（requests/psutil/PIL/websocket + 本地模块）全 hidden-import；构建机先 `pip install` 它们 |
| **数据写进 `resources\`** | 配置/记忆/日志都跑进安装目录的 `resources` 子目录 | `app_ui.DATA_DIR`：frozen 且父目录名是 `resources` 时往上跳一层 |
| **装完卸载/重装** | 卸载后目录里还留着 config/记忆 | 这是**故意**的（重装不丢记忆）；要彻底干净就手动删安装目录 |
| **`tar.exe -a` 打的 zip，资源管理器说「无效」** | 双击 zip 报「Windows 无法完成提取…文件夹无效」，但 `Expand-Archive` 能解开 | libarchive 写的 local header 里 method/size 是流式写法（csize=0、标志位不对），`zipfldr.dll` 不认。打包必须用 `[System.IO.Compression.ZipFile]::CreateFromDirectory($dir,$zip,Optimal,$false)`（deflate + 正规中央目录）。验收方式：`(New-Object -ComObject Shell.Application).NameSpace($zip).Items().Count` 必须等于真实条目数，别只信 `Expand-Archive` |
| **并行分片下 GitHub release 会把 zip 下坏** | 字节数和 `Content-Length` 完全一致，但 `zipfile` 逐条解压时报 `Bad CRC-32`（V1.2.2 的 `wrapper.node`、`LightQuic.dll`） | 别用「8 分片 + 多镜像轮转」凑速度。用单流 `curl -L`（实测 gh-proxy.com 单流 13MB/s，8 秒下完 118MB），下完必须逐条 `zipfile.ZipFile(...).open(i).read()` 校验 CRC；`testzip()` 只报第一个坏条目 |
| **5MB 探针测速不代表真实速度** | 探针 `Range` 请求 83KB/s，同一个源整文件单流 13MB/s | 评估下载源就真下一个文件；`Range` 请求常被代理单独限速 |
| **PowerShell 脚本里有中文** | 语法错误、乱码（`表达式或语句中包含意外的标记`） | Windows PowerShell 5.1 按 ANSI 读不带 BOM 的 UTF-8：脚本要么全英文、要么存成 UTF-8 with BOM |
| **Playwright 打进包了但没有浏览器** | 用户机上点「帮我查」报 Executable doesn't exist | `chromium.launch()` 不带 channel 只会找 `ms-playwright` 缓存；打包版必须按 `{}` → `{"channel":"msedge"}` → `{"channel":"chrome"}` 依次退，最后才退 HTTP 抓取 |
| **tauri 编译开始了才改前端** | 装出来还是旧页面 | 前端资源在 `cargo build` 阶段被嵌进 exe；`Compiling desktop` 一出现就别再改 `index.html`，改了要整包重跑 |
| **开关只放在新 Tab 里** | 用户说「没找到开关」 | 用户在需求里点名的地方（设置页）也得有入口或同款卡片，别自作主张只放新页面 |
| **只改 `app_ui.DATA_DIR` 不够** | `config.json`/`personas.json` 仍出现在 `resources\`（V1.2.2 实测） | `config.py`/`memory.py`/`personas.py`/`i18n.py` 等各按 `sys.executable` 算 `DATA_DIR`。必须在 `backend_server.py` **import 业务模块之前** `os.environ.setdefault("QQ_AGENT_DATA_DIR", _resolve_data_dir())`，`app_ui` 算完再回写一次 |
| **`publish()` 按大小判断「已最新」** | 坏包换好包后仍不进包（大小恰好相同） | 换离线包时先删 `desktop/src-tauri/resources/napcat_bundle.zip`，或给脚本加 `--force` |
| **改了前端却不生效** | 装箱后的前端是**嵌进 exe** 的；不 `(Get-Item src-tauri\src\lib.rs).LastWriteTime = Get-Date` 时 `cargo build` 也报 Finished，但资源没更新（V1.3.0 实测两次） |
| **`bootMask` 把免责协议挡住** | `#bootMask` 是 z-95、`#discMask` 是 z-70；把「等用户点同意」的 `await` 塞进 boot 的 `Promise.all` 就会永久卡住加载层。规矩：**boot 里不许等用户操作**，这类等待一律异步旁挂（V1.3.0） |
| **两个 `cargo build` 抢锁** | 后台 job 和前台同时建 → `failed to run custom build command` + `另一个程序正在使用此文件 (os error 32)`；先 `Get-Process cargo,rustc,link` 杀干净（V1.3.0） |
| **只带源码不带解释器** | 音视频模块第一版只把 `av_server.py`+`av_core/`（0.62MB）塞进包，用户机器没装 Python 就整块功能不可用（V1.3.2 被当场驳回） | 用 `build_av.py`（PyInstaller `--onefile`）打 `av_server.exe`（145.2MB，自带运行时），`av_bridge` 优先 spawn exe；**凡是「后端自己拉起的第二个进程」，都得是 exe，不能是 .py** |
| **同一个 145MB 在包里躺两份** | `build_backend.py` 若继续 `--add-data resources/av_module`，backend exe 会从 69MB 涨到 215MB，安装包里同一份数据出现两次 | 构建脚本先判断 `av_server.exe` 是否存在：存在就只让 Tauri 带 `resources/av_module`，不再塞进 backend exe |
| **PyInstaller 打完不删中间件** | `resources/av_module/build` + `dist` 又占 145MB，`sync_av_module()` 一拷就进安装包 | `build_av.py` 在拷贝完产物后 `shutil.rmtree` 掉 `build`/`dist`；`sync_av_module()` 的 `ignore_patterns` 也排除 `build`/`dist`/`*.spec` |
| **`GET /api/{method}` 是第二个写入口** | 三道安全校验全写在 `_security_mw` 的「非 GET」分支里，于是 `GET /api/save_settings?args=[…]`、`GET /api/set_codeword`、`GET /api/stop_agent` 全部 200 且真生效 —— 一个 `<img src>` 就能改配置（QA 终审 P0，CVSS 8.1） | 分发层先判「只读方法白名单」，其余 GET 一律 405；来源校验（`Sec-Fetch-Site`/`Origin`）挪到方法判断**之前**。**教训：安全校验不能挂在「HTTP 动词」这种可协商的东西上** |
| **`/rpc` 是绕过 5701 全部门禁的侧门** | `web_server.py` 的 `do_POST` 直接 `getattr(api, method)(*args)`，Origin/JSON/票据一个都没做，同一方法走 5701 被挡住、走 8765 畅通（QA 终审 P0，CVSS 9.0） | `/rpc` 加 Content-Type(415) → 来源(403) → 危险方法票据(403)；打包版根本不开网页版（`INDEX` 在 `_MEIPASS` 里不存在，之前是「口子开着、界面 500」） |
| **`_secret_keys` 名单齐全 ≠ 真的加密** | `provider_keys` 在名单里、日志也打了 `***`，但加密分支只处理 `cloud_api_key`/`codeword_token`，多厂商 Key 表照样明文落盘 | 名单只用来打日志；**加密必须按 key 分支写**，新增敏感键时先看 `save_settings` 里有没有对应 `elif`。另：`get_config` 过滤别用子串，`max_tokens` 里也有 `token`，会误伤 |
| **危险操作回 200 + `{"ok":false}`，curl 看着像通过** | 票据缺失时 `call_method` 返回普通 dict，HTTP 状态仍 200，QA 自动化全部误判 | 状态码要跟着语义走：缺票据 **403 + `code:"ticket_required"`**，GET 写方法 **405**，跨站 **403** |
| **拿 `Sec-Fetch-Site` 当一票否决，把自家界面打死** | 抢修第一版把「`cross-site` → 403」提到所有方法之前，结果安装版界面每 2 秒一次的 `GET /api/get_status` 全 403（`agent.log` 40 秒 360 条拒绝），用户报「一直连不上后端」；而我用 `curl -H "Origin: http://tauri.localhost"` 自测全绿 —— curl 不会被标 cross-site | **判据是 Origin，不是 `Sec-Fetch-Site`**：带 Origin 且白名单 → 放行；带 Origin 不在白名单 → 403 `bad_origin`；**没有 Origin 却标 cross-site** → 403 `cross_site`。前端在 `tauri.localhost`、后端在 `127.0.0.1:57xx`，按站点算本来就是跨站 —— **改了安全策略必须真的打开界面看，不能只 curl** |
| **公告数据不跟版本走** | `notice.py` 的 `NOTICES` 手写在代码里随包发布，发版时没人提醒改；新包首启还在讲 1.1.5/1.1.6 的旧事，用户以为装错版本（QA 终审 P3） | 内容硬编码、没有「版本号自检」；打包脚本不校验公告 | 发版清单加一条「公告标题必须含当前版本号」；更稳的做法是让 `打包发布.py` 断言 `NOTICES[0]` 里出现 `APP_VERSION`，不一致就报错 |
| **兜底话术被当成「模型连通」** | `chat_probe` 用 `ask_model(allow_fallback=True)`，模型没开也会拿到「脑子卡壳了……」并回 `ok:True`，用户误判连通正常（QA 终审 P2） | `allow_fallback=True` 的语义是「保证非空」，不是「成功」；调用方用 truthy 判断就分不出真假 | **判断连通性必须 `allow_fallback=False`**；返回体里显式给 `fallback` 字段，前端按 `ok===false` 显示红色原因 |

| **新页面 section 套进了上一个 section 里** | 音视频页整块被写在 `<section id="tab-admin">` 内部；HTML 合法（13 开 13 闭）、JS 不报错，点 tab 时 `tab-av` 自己也变 `display:flex`，但祖先 `tab-admin` 是 `display:none` → 用户看到整页空白 | 只校验了「标签开闭数量相等」；盲抄 4000 行 HTML 的缩进没核对层级 | 新增/搬动页面后必须用 CDP 断言 `section.parentElement.tagName === 'MAIN'`（不能只看 `display`），再 `PrintWindow` 截图肉眼看 |

### 6.3 逻辑类（V1.1.7 的教训）

**V1.3.0 新增七条（都是「看着安静、其实致命」的）**

- **`tab` 少一个 `overflow-auto` 就等于把内容切掉**：`main` 定了 `height: calc(100vh - 105px)`
  却**没设** `overflow`（也别设 `overflow:hidden`，见下条），section 又各自 `h-full` ——
  只要某个 section 少了 `overflow-auto`，内容比窗口高就直接溢出到窗口外被切，
  页面看着像「卡片被裁一半」，而且**没有滚动条能救**。
  V1.3.0 里 `#tab-memory`、`#tab-persona` 就是这种。现在统一
  `main > section{overflow-y:auto}`（聊天页 `#tab-console` 例外，它自己有滚动位置）。
- **别给 `main` 加 `overflow:hidden`**：免责协议/公告这些是 `main` 里的 `fixed` 浮层，
  祖先一旦建立包含块就会被裁掉 —— 实测直接表现为「协议根本看不见」。
- **局部 helper「先用了、后声明」也会静默带走整块**：`const on = (id, fn) => …` 写在函数下半部分，
  上半部分先调 `on('btnX', fn)` → `ReferenceError: on is not defined`（TDZ）。
  和下面那条一样，抛在大脚本块顶层，**同块后面全部不执行**，`node --check` 依旧全绿。
- **`async` 被换行拆开**：写成 `async` 单独一行（后面跟注释或换行再 `function f()`）在语法上**完全合法**，
  运行到那行却抛 `ReferenceError: async is not defined`。如果它在这个 `<script>` 块的顶层，
  **同块后面所有语句都不会执行** —— 于是 `boot()` 的 `DOMContentLoaded` 注册、
  一大票事件绑定全部消失，界面永远停在加载页。`node --check` 检查不出来（语法是对的）。
  线上表现：白屏 / 转圈到底 / 弹窗顺序全乱。排查：在 `<head>` 最前面装 `window.onerror`，
  把错误直接画到界面上截图；装在页面末尾的话，前面块抛的错一条也收不到。
  结论性做法：**首启免责协议已经单独成一个 `<script>` 块**，不再和容易出错的业务代码同居。
- **DOMContentLoaded 不能当唯一启动入口**：打包版里如果它没注册成功，`boot()` 就永远不跑。
  现在 `boot()` 有幂等标记 `window.__BOOT_STARTED` + 一条 800ms 兜底启动，两条路都走一遍也只跑一次。

- 「失败被静默吞掉」是最难查的 bug：`acquire` / `except` / 早退分支，一律打日志。
- 测试「未知方法」不要拿真实方法名试（`install_napcat` 真的会开始下载，把会话挂住还建了个 `x/` 目录）。
- 改 `index.html`（530KB 单文件）必须用 `read` 工具；`Get-Content` 的编码和行号都会骗人。

- **「开关点了没反应」先查变量名，别查样式**：`bridge.js` 里 `tray_running: trayOn`
  写错变量名 → 每次 `win_state` 抛 `ReferenceError` → 被全局 toast 成红字，
  而 `loadWindowPrefs()` 的 `.catch(()=>{})` 把失败吞成 undefined → 开关状态永远是错的。
  教训：**前端 `catch` 不许空着**，至少 `console.warn`，否则「看起来没反应」永远查不出原因。
- **「QQ 登不上」先数进程，别猜网络**：`launch()` 如果不管「已经起着」，
  每次点击/自动拉起都会多开一对 node 进程；几十个实例抢 3000/3001，
  后来者顶掉先来者，**二维码指向的实例已经死了**，扫码当然没用。
  现在 `launch()` 第一件事是 `running_pids(dir)`：在跑就直接返回，不重复开；
  旧实例先 `stop_all()` 清场。
- **进程在 ≠ 端口通**：NapCat 是扫完码才开 3000/3001，用端口判定「有没有跑」
  会把「等扫码」误判成「没在跑」，用户于是被引导去重复启动 —— 正好触发上一条。
  判定要以「进程在不在」为准，端口只用来判「登录了没有」。

- **测 ReAct 循环时，假模型不能按「第几次请求」返回**：`providers` 会先发一次预热请求
  （内容就是「你好」），计数器一到就先被预热吃掉，于是 ACTION 变 FINAL、循环 0 步结束，
  看起来像「模型不肯动手」。假模型要按 prompt 内容判别（含「现在输出下一步」→ ACTION）。
- **工具函数里的 `_check()` 抛出的 `EmergencyStop` 必须被兜住**：它本来是为了「立刻切断」，

- **Playwright 别覆盖 UA**：给 `new_page(user_agent=…)` 之后，Bing 会返回另一种版式，

  现在不覆盖 UA，并且 `bing → cnbing → ddg` 三引擎轮转，谁先出结果用谁。
- **`json.dumps` 写进 `.py` 会产出 `true/false/null`**：那是 JSON 字面量，Python 不认（`NameError: name 'true'`）。
  往源码里塞数据结构时要 `re.sub(r'(?m)(:\s*)true\b', r'\1True', seg)` 转一遍，或者干脆手写。
- **用 `find("NOTICES = [")` 这类宽松锚点会命中 docstring 里的示例**（本项目的 `notice.py`
  开头正好写着「往下翻到 NOTICES = [」）。这个坑我栽了两次：一次把文件头整个覆盖，
  一次把公告插进 docstring 里。**改源码前先 `re.search(r'(?m)^NOTICES = \[', t)` 锚行首**，
  改完立刻 `import` 一下验证语法。
- **把「同一个 QQ 不能同时两个客户端在线」当成能绕过的限制**：NapCat 是自带 QQ 内核的独立进程，
  不是挂在用户已打开的 QQ 上。用户视角却是「明明 QQ 登录了为什么不直接连」，所以正确做法是
  **自动接管 + 说清代价**（`napcat_auto_takeover` 默认开：`probe()` 判 `qq_client_busy` →
  `quit_qq_client()` 关掉本机 QQ → `launch(close_qq=True)` 用缓存快速登录，不扫码），

**V1.5.0 新增五条（Agent 闸门与自省的坑）**

- **把令牌放在进程内存里，等于给自己埋雷**：dev 模式后端会被壳重拉，`_CHALLENGES` 字典一清空，
  前端拿着旧令牌就永远「已过期」。改成**无状态 HMAC**：`<时间戳>.<签名>`，密钥落 `<数据目录>/agent_gate.key`，
  `verify()` 自己算签名 + 校验等待时长，进程重启也不影响。
- **`"%.3f" % ts` 自带小数点，别拿 `.` 当分隔符切**：`1761.234.sign` 用 `split(".")` 切出 3 段，
  校验永远失败；要么 `rsplit(".", 1)`，要么换别的分隔符。
- **`call(method, {...})` 不是「按名字传参」**：桥接层把第一个参数原样塞进 `args` 数组，
  后端收到的是 dict 而不是字符串 —— 前端要么 `String(x)`，后端要么 `isinstance(token, dict)` 兜底。
- **调试壳认 exe 不认源码**：`target\debug\resources\backend_server.exe` 的优先级高于 `python backend_server.py`，
  新方法在调试壳里一律「后端缺少方法」时，先把两个 `backend_server.exe`（target 里和 `src-tauri\resources` 里）
  改名成 `.bak`，测完改回来 —— 否则 `cargo build` 会报 `resource path resources\backend_server.exe doesn't exist`。
- **`ask_model_raw()` 返回的是字符串**：别按 `r.get("content")` 取（会 `AttributeError: 'str' object has no attribute 'get'`），
  写 `if isinstance(r, dict): r = r.get("content") or r.get("text")` 再 `str(r or "")`。

**V1.5.2 收尾新增四条（搜索与日志）**

- **「先浏览器后兜底」= 用户干等一分钟**：`tool_web_search` 原来串行跑 Playwright 三个引擎
  （每次 `goto` 20 秒），全失败才走 HTTP —— 而 HTTP 抓结果页两三秒就有 5 条。
  实测一句「查天气」**52 秒（源码）/ 82 秒（打包版）**。
  改「先 HTTP 并发抢（3 引擎 `ThreadPoolExecutor`，单 6 秒、总 9 秒），拿不到才开浏览器（总预算 16 秒）」
  → **6.4 秒**。教训：**能不用浏览器就别用**，浏览器只适合「必须点/必须渲染」的场景；
  兜底路径如果比主路径快，那它就该是主路径。
- **`as_completed(timeout=)` 超时会丢掉已经回来的结果**：`except TimeoutError` 里如果直接
  返回失败，那些 `fut.done()` 的 Future 结果就白跑了。正确姿势：超时后遍历 `futs`，
  把 `done() and not cancelled()` 的逐个 `_http_parse(fut.result())`，有用就用。
- **`re.subn(pattern, block, src)` 的 replacement 会被当转义串解析**：`block` 里若有 `\n`
  就变成真换行，写进 `.py` 立刻 `SyntaxError: unterminated string literal`（这个坑我已经踩了两次）。
  必须写 `re.subn(pattern, lambda m: block, src)`。
- **Agent 工具自测必须先开开关**：`agent_test_tool` 走 `_agent_exec`，而 `execute_code`/`web_search`
  都受 `agent_code`/`agent_web` 控制，默认关 → 测试全是「工具开关是关的」。
  脚本里先 `save_settings({agent_web:true, agent_code:true, agent_enabled:true})` 再测真链路。

**V1.5.3 新增五条（三个 P0 全是「自己的机制把自己锁死」）**
- **if let Some(x) = mutex.lock().unwrap().take() { mutex.lock() } = 同一把锁重入**：
  if let 的临时 guard 活到语句结束，里面再 lock() 就是同线程二次上锁，std::sync::Mutex 直接卡死
  —— 表现是「关窗口没反应、进程赖着不退」。先 let x = mutex.lock().unwrap().take(); 单独一行释放锁，再干活。
- **安全闸把「退出」也拦了**：_DISCLAIMER_FREE 漏了 quit_app/win_close，用户不同意免责协议时点 ✕
  被自己的 403 挡回去 —— 退出、最小化、问窗口状态都不碰数据，必须放行。
- **stdout 被壳接管后 print(flush=True) 会抛 OSError: [Errno 22]**：为 Rust 打印端口那一句在管道断开时
  掀翻 main()，后端秒退、而壳死等 45 秒 —— 用户看到的是「点了没反应」。所有启动期打印走 _safe_print()，
  端口另写 %LOCALAPPDATA%\\xiaojingyu-console\\backend.port 供壳兜底读。
- **清理临时目录「删不掉就叠后缀」= 自己造长路径**：_MEIxxx 删不掉就改名成 .xjydel，下次再叠一层，
  路径越叠越长，最后 
mtree 连打开都失败（Windows 260 字符上限）。改名只能是兜底、且只做一次，
  真正删除用 \\\\?\\ 前缀（UNC 走 \\\\?\\UNC）；另外 	empfile.gettempdir() 与 onefile 解压目录
  未必同一个（这台机器前者 D:\\Temp、后者 %LOCALAPPDATA%\\Temp），必须几处都扫。
- **MessageBoxTimeoutW 在 user32 导入库里没有符号**（LNK2019）—— 想「弹个框但别卡住」只能
  「后台线程 MessageBoxW + 主线程 
ecv_timeout」，别指望那个未文档化 API。

- **懒 import 的库 PyInstaller 一定看不见**：`onnxruntime` / `tokenizers` / `numpy` 都在函数里

## 九、V1.6.0 的决定：`agent.py` 暂不拆包（下一轮的交接说明）

**结论先写在这：V1.6.0 不拆 `agent.py`，按现状封版。** 拆包单独排一轮，按「切香肠」的方式切。

### 9.1 为什么暂缓

`agent.py` 8300 行、几百个模块级全局量（`LM_MODEL`、`MEMORY_MODE`、`HUMANIZE` 这一批），别的模块到处 `import agent` 再读这些量。真要一次拆成 `a_/b_/c_`，等于同时动 500+ 处引用，而且失败形态特别恶心：

- 聊天照常，但「关心计划 / 语音顺序 / 事件提取 / 说说」里某一条悄悄不工作了；
- 没有异常、没有日志，只有用久了才发现「它今天怎么没主动理我」；
- 现有的 `tests/` 覆盖不到这些边角（它们多数是定时器线程里的行为）。

V1.6.0 这一轮已经动了导航骨架、删了程序生图、加了性能预警，**同一版里再动 500 处引用，出问题根本分不清是谁干的**。所以按用户确认的方案：先稳定，再拆。

### 9.2 下一轮怎么拆（切香肠，不是推倒重来）

1. **第一刀只切叶子模块**，纯函数、不碰 globals：
   - `text_utils.py`：`split_reply()`、文本清洗 / 时间词判定这类无状态函数；
   - `messenger.py`：`send_private_human()` / `send_group_human()` 这类「发出去」的薄封装（它们只依赖 few 全局，容易剥离）。
2. **每一刀都要有行为对照**：同一段输入分别跑旧实现与新实现，比对返回值 / 发出的消息 / 日志行。模板放进 `tests/`，跟着代码走。
3. **最后才考虑 `agent_state.py`**：把 globals 搬进一个模块级对象（`state.LM_MODEL` 这种），这是真正危险的一步，必须单独一轮、不夹任何业务改动，并把 `test_v132_qc / test_v140_agent / test_v153_* / test_v160_*` 全跑一遍。

### 9.3 三条禁令（写给下一棒）

- **不要在带业务改动的那一轮顺手拆包** —— 出问题时分不清是功能还是重构。
- **不要跳过行为对照** —— 「import 不报错、界面能开」不等于行为没变。
- **改 `agent.py` 之前先备份** —— 这个项目没有 git，历史上有两次把文件改残（`notice.py` 被截断、`napcat_mgr.py` 被截成 0 字节），都是靠备份 / `release\..._开源包.zip` 里的源码救回来的。

### 9.4 V1.6.0 之后仍待办的事（与拆包无关）

- macOS / Linux 实机验证（只能在对应平台打包）；
- 安装包体积（416 MB，主要是 Playwright Chromium + 音视频 exe + NapCat 离线包）；
- 卸载时「同时删除我的记忆」这个选项；
- 向导里的「已安装但版本旧」只判断装没装，没判断要不要升级。

### 3.37 「记得住」不是把历史堆更长，而是把结论留下来（V1.9.10）

| 做法 | 看着像 | 实际上 |
|---|---|---|
| 历史窗口越开越大 | 记得更多 | token 爆炸、前缀每轮都变、缓存全废，最后还是要截断 |
| 一天一篇日记 | 有记忆 | 上下文断在下午，她就「失忆」到晚上 |
| **几小时一篇快照 + 强制注入** | 多花几次模型调用 | 任何时刻都能从最近 3 篇里接上话，成本可控 |

三条硬规矩：

1. **易变的东西一律放最后**：时间、情绪、临时召回，全部拼在最后一条 user 消息末尾；
   system 段只放「这个小时不会变」的内容，云端前缀缓存才有意义。
2. **写进历史的必须是结论，不是原始数据**：图片写「识别内容为：一碗白米饭」，
   不写 base64、不写空标记；否则下一轮模型只能反问「买的啥」。
3. **状态要真的落盘**：`save_state()` 不吃参数这件事，被 `except` 吞了好几版；
   「我以为存了」和「存了」之间，只差一次 `read` 回来验证。

### 3.35 「放宽一点点」就是换了个信任模型（V1.9.7）

V1.9.6 我为了让安装包能启动，把「清单里必须有主程序」改成了「有主程序才查」。
当时的自我说服是「安装包的清单本来就只覆盖 resources，卡这条等于谁都起不来」。
结果：攻击者把包根清单换成**安装包里那份公开的、只覆盖三个文件的清单**，
改过的主程序就合法了 —— 一行 `if` 的放宽，等于把「验签」降级成「随便有个签名就行」。

| 问法 | 错误答案 | 正确答案 |
|---|---|---|
| 这份清单能证明什么？ | 「文件没被改过」 | 「**这些**文件没被改过，别的文件它什么都没说」 |
| 清单缺主程序怎么办？ | 那就不查主程序 | 说明这份清单没资格给主程序作保 → 拒绝启动 |
| 目录里有多份清单？ | 挑一份能过的 | **全都得过**；过不了就点名让人删 |
| 谁有权决定「跳过检查」？ | 代码里的兼容分支 | 没有人。兼容要在打包期解决（把 exe 签进清单） |

两条硬规矩（沿用 V1.9.2/V1.9.6）：

1. **校验的宽松度只能由「待验对象的性质」决定，不能由「当前目录长什么样」决定** ——
   后者是攻击者能改的。
2. **兼容性问题在打包期解决**，不要留到运行期用 `if` 绕过去；绕过去的那条路
   迟早被当成攻击路径。

同批修的另外两处：`_manifest_rels()` 只认 `root/manifest.sha256`，而安装布局的
清单在 `root/resources/` 下 —— root 上提之后找不到清单，于是**每台装出来的机器
都会被判篡改**（自测第 2 条抓到的）。以及恢复工具「按文件名选包」等于把投毒入口
交给文件名。

### 3.38 「辅助调用」也在花你的钱（V1.9.11）

一条消息两次模型调用，主回复那边早就三段式了，可情感判定那次一直带着时间戳 ——
**前缀缓存的前提是「前缀逐字节一致」，多一个「11:50」就整段作废**。

| 容易忽略的地方 | 为什么会漏 | 现在怎么做 |
|---|---|---|
| 辅助/打分调用 | 只想着主线答案要缓存，忘了打分也要 import 一次 | 凡是「只要 JSON」的调用，system 用固定短串 + `no_time=True` |
| 默认参数 `system=None` | 默认值悄悄取整份人设，谁也没注意它带时间 | 需要稳定的调用必须**显式**传 system，不靠默认 |

1. **凡是进 system 的内容，先问一句「它会不会变」** —— 会变的（时间、情绪、临时状态）一律放最后一条 user。
2. **排序/比较类逻辑不许「非数字就记 0」** —— 塌成 0 的后果往往不是排错，而是**静默选错基线**。

### 3.39 别把能力写成剧本（V1.9.11.1）

给模型加能力，最危险的写法是**替它预设动机**：「傲娇的人会偷偷换」。
这句话对傲娇成立，但对「软萌」「高冷」「纯助手」是错误指令 —— 它们会以为自己不该用这个工具。

| 写法 | 问题 | 改法 |
|---|---|---|
| 「如果你傲娇，就……」 | 把人设当条件写进代码，其他性格被排除 | 「你拥有这个能力；怎么用按你的人设与三观自行决定」 |

### 3.40 「我已经重启了」要能被进程号证明（V1.9.11.2）

前端那句「正在重启 Agent」，底下调的是 `start_agent()`；而 `start_agent()` 见进程活着就
`return {"ok": True, "msg": "Agent 已在运行中（PID …）"}`。于是：

- 界面：重启成功 ✅
- 现实：旧进程还在，`SYSTEM_PROMPT` 还是老的一份，人设没变

| 症状 | 真因 | 硬规矩 |
|---|---|---|
| 换人设不生效 | 「启动」被当成「重启」 | 重启必须是 `stop → wait → start`，返回体带 `restarted` 与 PID |
| 动手模式口吻不对 | `run_agent_task()` 直接用模块级 `AGENT_SYSTEM_PROMPT` | 凡是「按当前人设说话」的地方，必须在**调用前**重读，不许用启动时快照 |
| 日记里出现 `[CQ:image,…]` | 原始消息直接入库/入 prompt | 面向人的文本（日记、记忆）出口处统一洗一遍 |

验收标准：**能指出「这一次」是新进程** —— `t_e2e.py` 断言的是 PID 变化 + 新进程日志里
`已加载「阿冷」`，而不是「接口返回 ok」。

**同版补的三条（QA 发版前）**：

| 现象 | 根因 | 修法 |
|---|---|---|
| 分享视频的气泡从「》」开始 | 拆句正则只认标点，不认《》「」"" 成对符号 | 拆前把成对符号换成占位符、拆后还原；分享本身 `no_split=True` 整条发 |

### 3.42 「让她调工具」在聊天链路里是句空话（V1.9.12 验收后补）

| 症状 | 真因 | 正确做法 |
|---|---|---|
| 发图说换头像，她嘴上答应但资料没动 | 聊天链路走 `ask_model`，**没有 `tools` 字段**，`update_profile` 只在动手模式的工具表里 | 要么给聊天开受控工具，要么让模型用**文本控制标记**表达决定、由系统执行（本次选后者） |
| 用户发了图，她回「把图片发给我」 | 抢答分支只看文本、不看有没有图 | 抢答前先看 `_event_has_image(event)` |
| 合并窗口调小就丢消息 | 合并路径复用「冷即丢」的 `can_reply()`，被挡下时静默 return | 冷却挡下要**放回缓冲重试**并留日志，不能无声消失 |
| 控制标记能被用户自己打出来 | 标记解析没区分来源 | 用户文本先 `_strip_profile_marks`，只认模型输出 |

两条硬规矩：
1. **提示词只能要求模型做「它能做的事」** —— 先确认那条链路上有工具通道，再写「请调用 X」。
2. 任何「静默丢弃」的分支都要么改成排队，要么至少留一条日志；否则用户只看到「她没回」。

### 3.43 定时器要「重置」，不能「只起一次」（V1.9.13）

| 症状 | 真因 | 这次的做法 |
|---|---|---|
| 连发三条只回了第一条 / 最后一条被吞 | 轮询线程只在第一条时起，后面只改 `last`，线程一旦退出就再也不合并 | 每条消息 `cancel()` 旧 `Timer` 再建新的 —— 「最后一条之后安静 N 秒」 |
| 合并后的文本她看不懂「这是好几句」 | 老格式是 `用户：第一句 用户：第二句`，没有边界 | 编号 `[消息1：…][消息2：…]`，并把图片/表情包转成 `[图片]`/`[表情包：狗头]` |
| 冷却一挡整批消失 | 冷却判断在合并路径里 `return` | 整批塞回缓冲 + 新定时器重试 + WARN 日志 |

硬规矩：
- **「等一等」要用可重置的定时器**，不要让一个线程自己数秒；
- **排队的边界是会话锁**：宁可等，不能让两轮回复交叉。

### 3.44 三件事叠在一起，就成了「每次都要扫码」（V1.9.14）

- **选号不是"能用"，是"日志排序"**：`quick_login_uins()` 给的是 NapCat 自己扫出来的名单顺序。名单里有号的登录态早就废了，照样排第一。
- **强杀把登录态搞坏了**：`taskkill /F` 不给 QQ 落盘的机会，下一次"快速登录"直接被判失效。**我们自己在制造"登录态已失效"**。
- **"接管"默认等于"退掉你的 QQ"**：用户只想连上机器人，并不想关掉自己正开着的 QQ。

硬规矩：

1. 任何"会动用户别的程序"的动作，默认必须**不做**，要用户明确点一次才做。
2. 关别人的程序先发**正常关闭**（`taskkill` 不带 `/F`），等不到再问；**永远不要一上来就强杀**。
3. 候选顺序不要相信上游给的顺序，要自己记录**成败**（`_uin_state.json`：`last` / `bad` + TTL）。
4. 记住的两个方向别搞混：**"上次成功" ≠ "现在能用"**，"最近报失效"才是真的坏。

## 十二、模块化拆分经验（V2.0.0，交接必读）

> 这一节是给下一个接手的人（或 AI）看的：为什么要这么拆、哪些坑已经踩过、下次怎么拆。

### 12.1 先评估，再动手

拆之前先做一次结构体检（AST 就够）：

- 有多大：`agent.py` 12145 行 / 353 个 def·class / 320 个模块级变量
- 有没有现成的循环引用：**没有** —— 顶层只 import 叶子模块（config / diary / providers / usage / qzone / imagegen / stickers / personas / emotion），没有任何模块反向 import agent。所以风险不在「已有循环」，而在「新拆出来的 core↔agent 循环」
- 哪些名字是**活配置**：`_reload_constants()` 用 `g = globals()` 写了约 90 个派生常量，由 `_live_all()` 在配置指纹变化后就地刷新

**结论先行**：core 里绝对不能 `from agent import LM_MODEL`，否则「设置改完不生效」这个老毛病会以新形态回来。

### 12.2 阶段划分（按风险从低到高）

| 阶段 | 内容 | 风险 | 为什么这个顺序 |
|---|---|---|---|
| 一 | 纯函数（utils）+ 发送层（sender） | 低 | 没有状态、不被别人反向依赖；先跑通整套工具链 |
| 二 | 提示词（prompt_builder）+ 通信（llm_client） | 中 | 活配置最密集，正好此时把 `_sync()` 机制压出来 |
| 三 | 后台循环（tasks） | 中高 | 锁与状态最多，必须验证「单例没分裂」 |
| 四 | 提取 / 空间 / 流水线（extract / qzone_flow / pipeline） | 高 | 互相调用最密、异常分支最多 |

每阶段固定动作：搬 → `py_compile` → `import agent` → 冒烟（`hasattr` 全覆盖 + 穿透测试）→ **12 套 433 项回归** → 才进下一阶段。

### 12.3 万用工具链（这套脚本的思路可以照抄）

1. **结构评估**（AST）：列出所有顶层 def / class / 赋值，标行范围、字符数、引用的外部名字。
2. **依赖报告**：给一个名字，报「行范围 / 用到哪些模块级名字 / 被本模块引用几次 / 全仓引用几次」。
3. **原样复制**：按 AST 把顶层块（含前置注释）整段复制到新文件，**不改一个字**。
4. **桥接清单**：复制后扫出「仍引用 agent 模块级名字」的清单 → 据此写 `_SYNC_NAMES`。
5. **按 AST 精确删除**：从 agent.py 删掉同样的行范围（删前 `ast.parse` 校验，删后再 `ast.parse`）。
6. **兼容导入**：把搬走的名字全部 `from core.xxx import (...)` 回 agent 顶部。
7. **静态体检**（见 12.4）。

一个必须遵守的细节：**按内容锚点定位，不要按「第 N 次出现」定位**。我在修一条分隔线时按「第一处 66 个短横线」删，结果删掉了另一个块的头，白改一轮。

### 12.4 AST 静态体检：根治「搬漏依赖」

搬移最容易出的错不是逻辑错，而是**漏名字**：某个只在异常分支/特定平台才走到的路径里用了一个没搬过来的名字，正常流程测不到，上线才炸。

脚本思路：

```
对每个 core/*.py 的每个函数：
    need = 该函数体里所有 Name(Load)
    have = 函数内绑定（参数 / 赋值 / for / with as / except as / 内嵌 def 名 / 推导式变量）
         ∪ 模块级绑定（def / class / 赋值 / import 别名）
         ∪ _SYNC_NAMES（本来就该由 sync 提供）
         ∪ builtins
    报 need - have
```

要点：

- **`_SYNC_NAMES` 必须排除**，否则输出全是噪音（我第一次没排除，报了 308 处，真正要修的只有十几处）。
- **闭包自由变量是假阳性**：报出来的名字若在**外层函数**里有绑定（`_fallback` 里的 `raw_text`、`_run` 里的 `edge_tts`、`_rel` 里的 `now_min`），属正常闭包，不用管。
- **推导式变量**（`m`、`t`、`v`）也是假阳性。

它在这轮里一次性抓出：`qzone_flow` 的 `ask_model` / `send_group_human` / `send_private_human` / `clean_reply` / `PQ_PRIO_BG`、`tasks` 的 `cfg_mod` / `diary_mod` / `qzone_mod` / `active_name` / `SYSTEM_PROMPT` / `send_to_session`、`prompt_builder` 的 `diary_mod` / `normalize_messages`、`llm_client` 的 `_data_path` / `MAX_CONTEXT_TOKENS` / `MIN_KEEP_MESSAGES` —— 全是回归测不到的路径。

### 12.5 三类真故障与对应纪律

| 故障 | 根因 | 纪律 |
|---|---|---|
| 自测直接崩（`通过 0 失败 -1`） | 漏 `import queue`（`queue.Queue` 未定义） | 搬块要连**标准库 import** 一起搬 |
| `NameError: _MEDIA_ONLY_HEAD` | 函数搬了，它依赖的 4 个正则常量没搬 | **常量也是依赖** |
| 回评论静默失败：`name 'active_name' is not defined` | `from personas import active_name` / `import qzone as qzone_mod` 是**导入别名**，桥接报告只统计「agent 自己定义的」名字，看不到 | 搬前先列「agent 顶部 import 进来的名字」，它们同样是模块级名字 |

### 12.6 三条不能破的性质（改这块代码前默念）

1. **活配置不能吃快照**：`LM_*` / `MOMENT_*` / `FEED_*` / `STICKER_ENABLED` / `SYSTEM_PROMPT` 这类由 `_reload_constants()` 就地刷新的名字，core 里一律 `_sync()` 现取或用 `_g.live()`，**不许** `from agent import`。
2. **单例不能分裂**：`state` / `sessions` / `mem` / `napcat` / `_FOLLOWUP` / `_CARE_SENT` / `_EXTRACT_LAST` / 各种 `Lock` —— 全项目只有一份，core 里只 import 别名或 sync，**绝不 new**。`start_*_thread` / `stop_*_thread` 因此故意留在 agent（它们会重新赋值线程句柄）。
3. **兼容层不能删**：`agent.py` 顶部 `from core.xxx import (...)` 是外部几百处 `agent.xxx` 的生命线。删一个名字就是一片红。

### 12.7 拆完的样子（方便你判断「该往哪加代码」）

| 你要做的事 | 去哪 |
|---|---|
| 加一个新模型参数 / 换个请求格式 / 调重试策略 | `core/llm_client.py` |
| 改她的说话方式 / 加一条系统规则 / 调记忆注入顺序 | `core/prompt_builder.py` |
| 加一个定时任务（几点干什么） | `core/tasks.py`（记得 while 体也 `_sync()`） |
| 改一条消息进来之后的处理步骤 | `core/pipeline.py` |
| 改记忆/事件的提取规则 | `core/extract.py` |
| 改空间（说说/评论）行为 | `core/qzone_flow.py` |
| 改发送方式（新消息类型、语音、表情包） | `core/sender.py` |
| 加纯函数（清洗、解析、换算） | `core/utils.py` |
| 需要 agent 的某个全局/函数 | 走 `core/globals.py`，别 import agent |
