# 小鲸鱼 V1.9.7.1 安全修复说明

> 这份文档只讲 V1.9.7.1 这一版：**改了哪几处（A–E）、为什么这么改、验证到什么程度、还剩什么没解**。
> 面向 QA、后续维护者，以及"半年后回来看这段代码的人"。
> 面向用户的一版一段说明见 `Docs\更新日志.md` 里的 `## V1.9.7.1` 一节。

---

## 0. 一句话

V1.9.7.1 是对《小鲸鱼 V1.9.7 逆向复测报告》的定点整改：只修**几处"修复本身带给用户的代价"**，
不加功能、不动界面、不动配置项、不动密钥体系。

| 编号 | 级别 | 症状 | 一句话改法 |
|---|---|---|---|
| A | P0 | 安装版一启动就报「被篡改」，遮罩卡死进不去 | `verify()` 定位清单时认 `resources\`，基准仍是安装目录 |
| B | P1 | 1.9.6 老用户升级后被判「防护章被换锁」，五个开关被强制打开 | 32 字节老格式静默采信，顺手补指纹升级成 48 字节 |
| C | P1 | 增量包按进程名杀进程，会误杀另一份安装、可能破坏正在写的库 | 按 `$Target` 路径前缀过滤，只关自己目录的进程 |
| D | P2 | 恢复工具的 `--dir` 不认安装包布局；验签器可被替换绕过验签 | `--dir` 也去 `resources\` 找清单；脚本内置 sha256 自校验；打包时交叉核对 |
| E | P0 | A 修完、自测全绿，用**真安装包**装一遍仍然自判篡改 | 安装包清单按「安装形态的字节」算主程序哈希；增量包带两份清单按布局挑 |

## 2. 威胁模型：这一版之后，什么能保、什么保不了

### 2.1 能保证的

1. **安装包 / 绿色版的每个文件都与发布者的清单一致**。签名是 Ed25519，私钥不在包里；
   安装版（清单在 `resources\`）、绿色版（清单在包根）现在走同一条验证路径，
   以及"包里同时存在多份清单"时**每一份都必须通过**（V1.9.7 的 Rust 侧规则，未回退）。
2. **恢复工具的来源包必须先验签**才允许写入目标目录；验签器自身与脚本成对，替换其一即被拦下。
3. **增量包不再影响别的安装**：关进程只看 `$Target` 目录内部，别的版本目录里的
   进程与正在写入的数据库不会被误杀。
4. **装出来的程序能通过自检**：安装包清单里的主程序哈希按「安装包里的字节」计算
   （打包器会改 3 个字节，见 E），安装版与绿色版各用各自的清单，增量包按布局挑，
   不会把绿色版的 exe 盖进安装目录。

### 2.2 保不了的（写清楚，别自欺）

| 边界 | 说明 | 现状 |
|---|---|---|
| 本地管理员可同时替换 `恢复官方安装.ps1` 与 `verify_bundle.exe` | 脚本内置 sha256 只能挡"只换一个"。两个一起换，脚本里那个常量也跟着换，自校验自然通过 | 天花板已在第 6 节写明；彻底解法是让恢复工具整体进主程序清单（排 1.9.8） |
| `guard.seal` 的指纹可被本地伪造 | 指纹 = `HMAC(secret_salt, key\|machine_id)`，而 `secret_salt` 就在本机程序里。拿到程序的人能自己造一份"合法"的 48 字节 seal | 这是**本地不可解之谜**：除非引入 TPM 或非对称签名（公钥在包内、私钥不在本机），否则任何本地校验都只是提高门槛 |
| 五个 exe 没有 Authenticode 签名 | 复测 N-18/P3，历史遗留（需代码签名证书） | 本版未做；验签体系走的是自建清单，不依赖系统证书链 |
| 分片加密的固定掩码（N-19/P2） | 与本章四处无关 | 本版未动，见第 6 节 |

> 换句话说：**这一版的对手是"想篡改安装包/想借更新包搞破坏的人"，不是"已经拿到本机管理员权限的人"**。
> 后者的边界与 V1.9.7 相同，没有变松也没有变紧。

## 3. 五处修复逐条

### A（P0）安装版变砖：`verify()` 只认包根清单

**症状**：安装包装完，双击 `小鲸鱼.exe` → 首屏遮罩「程序文件被篡改」，业务界面永远不加载。
增量包/覆盖安装同样中招。

**根因**：安装包把清单放在 `<安装目录>\resources\manifest.sha256`（Tauri 的 resources 目录），
而 `signing.verify()` 里 `mp` / `sp` 是写死的 `os.path.join(root, "manifest.sha256")`；
原先只有一个"当 root 自己就叫 `resources` 时把 root 上提一层"的特例，既没有让 `mp` 跟着走，
也覆盖不到"传进来的就是安装目录"这一实际调用。

**改法**（`signing.py`）：

```python
def _locate_manifest(root):
    """返回 (基准目录, 清单路径, 签名路径)。基准目录是清单里相对路径的起点。"""
    # ① root 自己有清单：绿色版（或安装版的包根残留）
    #    —— 若 root 叫 resources，基准上提到它的父目录（安装目录）
    # ② root/resources 有清单：安装版，基准 = root（安装目录）
    # ③ 传进来的就是 resources、清单在上一层：基准 = 上一层
    # ④ 都没有：返回 root/清单，让上层照旧报"找不到签名清单"（不放水）
```

`verify()` 里原来的三行（`mp`、`sp`、uplift）换成 `root, mp, sp = _locate_manifest(root)`。
**清单基准没有被放宽**：安装版的相对路径仍以安装目录为基准，与签名时一致 —— 不是"哪份宽松用哪份"。

配套：`find_package_root()` 补了 `resources\manifest.sha256` 分支。少了这半截，
`verify_program_dir()` 会顺着 exe 往上找三层都碰不到清单，报「向上找了 3 层都没找到签名清单」，
等于换了个理由继续拦住用户（这条是自测时抓到的，属于 P0 的另一半）。

**回归**：`tests\test_v1971_fix.py` 第 1 组 14 项 + 第 6 组 4 项（真实 Rust 壳 `--verify-self`）。

### B（P1）1.9.6 老用户的防护章假警报

**症状**：1.9.6 用户升到 1.9.7 后，日志出现
`WARN 防护章文件 guard.seal 被改过（前缀 legacy）—— 不采信其中的密钥，五个防护开关强制开启。`，
用户自己关掉的防护开关被掰开。

**根因**：V1.9.7 给 `guard.seal` 加了 16 字节指纹，格式从 32 字节变 48 字节；
老格式被归到 `seal_bad = "legacy"` → 与"被换锁"走同一条 fail-closed 分支。
**"分不清升级和伪造就先当伪造"** 在安全上说得通，但代价落在每一个没做错事的用户身上。

**改法**（`config.py::_guard_key()`）：

| `guard.seal` 内容 | 判定 | 是否改开关 | 是否重写文件 |
|---|---|---|---|
| 48 字节、`blob[32:] == _guard_fp(blob[:32])` | 采信 | 否 | 否 |
| 32 字节（1.9.5/1.9.6，DPAPI 包裹） | 采信（`legacy=True`） | **否** | **是**：升级成 `dpapi:`(32 字节密钥 + 16 字节指纹)，只记 INFO |
| 48 字节但指纹不对 | `fp` → 判换锁 | 是（五开） | 是（换新密钥） |
| 长度既非 32 也非 48 | `fp` → 判换锁 | 是（五开） | 是 |
| 前缀 `raw:` / 认不出 | `raw` / `unknown` → 判换锁 | 是（五开） | 是 |

三个关键细节：

- **密钥原样沿用**：升级只补指纹，`_guard_sig()` 的格式串仍为 `guard|1.9.4|`，
  用同一把密钥算出的签名不变 → 用户关掉的开关（`guard_sql` 等）在升级后保持原值。
- **`_GUARD_SEAL_TAMPERED` 不再被 32 字节触发**，也就不再触发"五开 + 重签"。
- **真伪造一点没松**：`raw:`、长度不对、指纹不对，仍然 fail-closed 全部强制打开。

写盘段改成 `upgrade` 标志驱动，并在 `_secg2._dpapi_available()` 为真时才写（
DPAPI 不可用的环境不写文件，下次启动重试升级，不会把老格式写坏）。

**已知的回退限制**：升级成 48 字节后，如果用户把程序**降级**回 1.9.6，那一版只认 32 字节，
会认为 seal 无效 → 重新生成密钥 → 判 `guard_sig` 不匹配 → 五开 + 报警。
一次性的、可恢复的（在 1.9.6 里重新设一次开关即可），我们不支持降级，但 QA 值得知道这个现象。

**回归**：第 2 组 10 项（32 / 48 / 24 字节 / `raw:` 四种 seal × 是否判篡改 × 五个开关取值 × 是否升级）。

### C（P1）增量包按进程名乱杀

**症状**：双版本共存（比如 `D:\小鲸鱼` 与 `E:\小鲸鱼测试`）的用户应用增量包时，
另一份安装的后端被一起杀掉；若那一份正在写记忆库，**用户数据可能损坏**。

**根因**：`apply_delta.ps1` 里两处都用 `Get-Process -Name backend_server` / `-Name 小鲸鱼`
扫全机器。名字是全局的，目录不是。

**改法**（`打包发布.py` 里的 `DELTA_PS1`，间接也改了打出来的 `apply_delta.ps1`）：

```powershell
function Get-TargetProcs {
    $names = @("小鲸鱼", "backend_server", "av_server")
    Get-Process | Where-Object {
        $names -contains $_.ProcessName -and $_.Path -and
        $_.Path.StartsWith($Target + "\", [System.StringComparison]::OrdinalIgnoreCase)
    }
}
```

- 更新前的占用检查 → `$busy = @(Get-TargetProcs)`，提示里明说"只关这个目录里的（别的安装不受影响）"。
- 验签后清场 → `@(Get-TargetProcs)` → `Wait-Process -Timeout 30` → 再取一次逐个
  `WaitForExit(10000)` + `Kill()`，清不掉才提示重启。

与 `Tools\恢复官方安装.ps1` 里的 `Get-TargetProcs(:261-276)` 同源 —— 同一种判断只写一次逻辑。

**回归**：第 3 组 5 项（有 `Get-TargetProcs`、按 `$Target` 前缀比对、全文无 `Get-Process -Name` 扫杀、
杀进程只经由该函数、PowerShell 解析器语法校验通过）。

### D（P2）恢复工具：`--dir` 不认安装布局 + 验签器可被替换

**症状 1**：把安装包装完的目录交给 `恢复官方安装.ps1 -Source <目录>`，或手跑
`verify_bundle.exe --dir <安装目录>` → `rc=4 directory has no manifest.sha256`。而脚本注释写着支持该用法。

**症状 2**：`verify_bundle.exe` 只被 `Test-Path` 检查过。把随便一个"永远返回 0"的壳换进去，
恢复工具就会把一个未验签的包写进程序目录 —— **验签这道门形同虚设**（复测 4.3）。

**改法**：

- `Tools\verify_bundle.py::verify_dir()`：先看包根清单，再看 `resources\` 清单（`md` = 实际存放清单的目录）；
  `manifest.sha256` / `manifest.sig` 落在 `md`，其余文件仍按包根解析。输出仍是纯 ASCII
  （PowerShell 5.1 抓 stdout 时中文会乱码），rc 语义不变。
- `Tools\恢复官方安装.ps1`：`$verifyExeSha256` 内置常量，`Test-Path` 之后立刻 `Get-FileHash` 比对；
  读不出哈希 → `Fail 2`「恢复工具可能损坏」；对不上 → `Fail 2`「不是随这个脚本发布的那个 —— 有人换过验签器」。
  **这一步在任何写入之前**，所以被换过的验签器不会造成任何副作用（自测确认：目标目录一个文件都没动）。
- `打包发布.py::step_tools_zip()`：出包时就核对 ps1 内置的那个 sha256 与 `Tools\verify_bundle.exe`
  的实际值，不一致直接 `SystemExit`；顺带检查 ps1 带 UTF-8 BOM（没有 BOM 的 ps1 在 PowerShell 5.1 下
  中文会变乱码并引发语法错误 —— 这次改动就踩过，见第 7 节）。

### E（P0）安装包里的主程序被 NSIS 打包器改了 3 个字节

**怎么发现的**：A 修完、54 项自测全绿之后，用**真的**装了一遍
（`小鲸鱼_x64-setup.exe /S /D=<临时目录>`），装出来的目录 `--verify-self` 依然 `rc=4`：
`resources\manifest.sha256：有 1 个文件对不上：小鲸鱼.exe（内容被改过）`。

**事实**（可复现）：

| 对象 | sha256 | 大小 |
|---|---|---|
| `desktop\src-tauri\target\release\小鲸鱼.exe`（构建产物；绿色版里就是它） | `4f47b272754fb55c745127514a64b89fd91c798ab3d948bd3034989fd9b9725d` | 5,364,736 B |
| 安装包装出来的 `小鲸鱼.exe` | `01b9d6a6f601b5cbcdb8485c09d51ed8c9ed2675824440af80dfb1281ba6725b` | 5,364,736 B |

- 只差 **3 个字节**：偏移 5056103 / 5056104 / 5056105（`.rdata` 段内）。
- 内容就是把 `__TAURI_BUNDLE_TYPE_VAR_UNK` 里的 `UNK` 换成 `NSS`（其余字符相同）。
- 排除项：PE 校验和两文件都是 0（偏移 328）；`TimeDateStamp` 都是 3350683764；尾部 64 字节一致
  —— 不是两次构建、不是杀软改写。
- 来源：`tauri-utils-2.10.2/src/platform.rs:357` 的
  `static mut __TAURI_BUNDLE_TYPE: &str = "__TAURI_BUNDLE_TYPE_VAR_UNK";`，
  `bundle_type()`（:361-378）把 `..._NSS` 映射成 `Some(BundleType::Nsis)`。
  改写发生在 **tauri-cli 的 NSIS bundler** 里（预编译二进制），且**只改它自己打进安装包的副本**。
  把构建产物里的这一处 `UNK` 手工替换成 `NSS`，算出的哈希与真装出来的 exe 完全一致（已实测）。

**为什么 A 修完还不够**：V1.9.7 起清单必须写着主程序，`step_tauri()` 又会比对
「清单里的主程序哈希 == 构建产物哈希」。这两条比的都是 `UNK` 那份，**全部通过**，
于是打出一个装完必然自判篡改的包 —— 检查没错，是检查对象错了。

**改法**（不碰 Rust、不改绿色版产物的任何一个字节）：

| 位置 | 改动 |
|---|---|
| `打包发布.py` | `sha256_of_installed_exe(p)`：读入字节，`UNK` 恰好出现一次时替换成 `NSS` 再算哈希（只改内存）；`swap_manifest_hash(text, rel, hash)`：只替换清单里那一行的哈希 |
| `sign_tauri_resources()` | 清单里 `小鲸鱼.exe` 那行改写成安装形态哈希 → `resources\manifest.sha256` 与安装包里的字节对齐 |
| `step_tauri()` | 两轮校验也改用安装形态哈希 |
| 绿色版清单 | 仍是 `UNK` 那份（绿色版跑的就是它）—— 两份清单各自说真话，不混用 |
| `step_delta_zip()` | 增量包额外带 `payload/install/manifest.sha256` + `.sig`，并在 `delta_manifest.json` 里加 `install_layout` 段（含 dest / sha256 / size），在签名之前写入 |
| `DELTA_PS1` | 先看 `<程序目录>\resources\manifest.sha256` 是否存在：有 → 用安装版那份（落到 `resources\`，并清掉包根误留的旧清单）；没有 → 用绿色版那份；安装版遇到不含 `install_layout` 的老增量包、或增量包里带了 `小鲸鱼.exe` → `Fail 2` 明确让人用完整安装包 |
| `backend_server.py` | `--verify-delta` 时把 `install_layout` 里的文件也按 sha256 核一遍（不能只让 ps1 自己比） |

**为什么要分两份而不是改 Rust 容忍差异**：容忍 3 字节差异等于给「改 exe」留一个合法窗口，
与 V1.9.7 的收紧方向相反；而改 Rust 超出了这一版「外科手术」的范围。

**回归**：第 7 组 12 项 —— 安装形态哈希算法、只改内存不动产物、只换目标行、
两布局验签、`find_package_root()`、**老做法（记构建产物哈希）在安装形态下仍然失败**（复现被修的雷）、
ps1 有布局分支且清单落 `resources\`、打包脚本会带安装版清单、后端会验它。

## 5. 产物与校验（V1.9.7.1）

`%RELEASE%` = `release\`。哈希在每次出包时可能因文档改动而变，以 `release\` 目录里实际文件为准，

| 文件 | 说明 |
|---|---|
| `小鲸鱼_V1.9.7.1_绿色版.zip` | 绿色版整包 |
| `小鲸鱼_V1.9.7.1_增量包.zip` | 从 1.9.7 升到 1.9.7.1（只含改动文件） |

| `小鲸鱼_1.9.7_x64-setup.exe` | 安装包（内部版本号仍是 1.9.7，见下） |

1. `Tools\verify_bundle.exe` 的 sha256 **等于** `Tools\恢复官方安装.ps1` 里

## 7. 这次踩到的三个坑（留给后来人）

1. **PowerShell 5.1 认 BOM**：用编辑器（UTF-8 无 BOM）保存 `恢复官方安装.ps1` 后，
   PowerShell 按 ANSI/GBK 解析，中文变乱码并抛
   `Unexpected token '}'` / `Missing closing '}'`。改 `.ps1` **必须保留 EF BB BF**，
   `step_tools_zip()` 现在会拦住没有 BOM 的版本。
2. **`verify_program_dir()` 依赖 `sys.frozen`**：自测时如果没有把 `sys.frozen = True` 且
   同时改 `sys.executable`，它会从 `__file__` 起算，测出来的"通过"是假通过。
   测试里的做法是同时设置这两项，并对"主程序在包根"和"Python 侧在 `resources\`"各跑一遍。
3. **别用合成包代替真安装**：A 修完后 54 项自测全绿，"清单在 `resources\` 也能验"这件事被反复证明，
   但真装一遍仍然 `rc=4` —— 因为合成测试里的 exe 是同一份拷贝，而真安装包里那份被打包器改了 3 个字节。
   **凡是"打包器会不会动我的文件"这类问题，必须用真产物验一次**。
   定位手法：`D:\临时文件\_xjy_build\diff_exe.py`（PE 段定位 + 逐字节 diff），
   确认差异只有 3 字节且落在 `.rdata` 之后，再去 cargo registry 里搜那个字符串常量。
